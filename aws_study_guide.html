VPC & Networking

The foundation — everything in AWS lives inside a VPC

Hour 1-2 VPC Core Concepts

  • VPC = your private network in AWS (like your own data center)
  • CIDR block = IP range. 10.0.0.0/16 gives you 65,536 IPs
  • Region = geographic area (us-east-1). AZ = physical data center within region (us-east-1a, us-east-1b)
  • Always deploy across 2 AZs minimum for high availability

Hour 3-4 Subnets, Route Tables, Gateways

  • Public subnet = has route to Internet Gateway. ALB lives here.
  • Private subnet = no direct internet. Your app + DB live here.
  • NAT Gateway = lets private subnet make outbound calls (Groq, Deepgram APIs) without being publicly reachable
  • Route table = rules: "traffic to 0.0.0.0/0 goes to IGW" or "goes to NAT"
VPC (10.0.0.0/16) ├── AZ-a │ ├── Public subnet (10.0.1.0/24) <- ALB, NAT Gateway │ └── Private subnet (10.0.3.0/24) <- ECS tasks, RDS ├── AZ-b │ ├── Public subnet (10.0.2.0/24) <- ALB (cross-AZ) │ └── Private subnet (10.0.4.0/24) <- ECS tasks, RDS standby

Hour 5-6 Security Groups

  • Security Group = firewall at instance/container level (stateful)
  • Stateful means: if you allow inbound, the response is auto-allowed
  • NACL = firewall at subnet level (stateless) — less common in interviews

Hour 7-8 Hands-on (Free Tier)

  • Log into AWS Console -> Create VPC with VPC Wizard (2 AZ, public+private)
  • Observe what it creates: subnets, route tables, IGW, NAT
  • Delete everything after to avoid charges
Interview Answer — "Describe the networking"
"I'd deploy in a VPC with 2 AZs for high availability. ALB sits in public subnets, ECS tasks and databases in private subnets. NAT Gateway lets containers call external APIs like Groq and Deepgram without being publicly exposed. Security groups restrict traffic — only ALB can reach ECS on port 8000, only ECS can reach RDS on 5432 and Redis on 6379."

ECS Fargate

Where your FastAPI app runs — serverless containers

Hour 1-2 ECS Concepts

  • Cluster = logical grouping (just a namespace with Fargate, no servers)
  • Task Definition = like docker-compose.yml for AWS (image, CPU, memory, ports, secrets)
  • Task = a running container instance
  • Service = ensures N tasks always running, connects to ALB, handles deploys
  • Fargate = serverless (no EC2 to manage). EC2 launch type = you manage servers

ALB + WebSocket + SSL

The entry point — where Twilio connects to your app

Hour 1-2 ALB Concepts

  • ALB = Application Load Balancer, Layer 7 (understands HTTP, WebSocket)
  • NLB = Network Load Balancer, Layer 4 (TCP only). Can't do path-based routing.
  • Listener = port 443 HTTPS with ACM certificate
  • Target Group = group of ECS tasks receiving traffic
  • Routing rules: /stream -> WebSocket, /voice/* -> HTTP, /health -> HTTP

Hour 3-4 WebSocket on ALB (Critical Topic)

  • ALB supports WebSocket via HTTP/1.1 Connection: Upgrade header
  • Once upgraded, connection is persistent + bidirectional — audio flows both ways
  • Idle timeout: default 60s. Set to 3600s for phone calls (long pauses are normal)
  • WebSocket connections are inherently sticky — pinned to one target after upgrade
  • Risk during deploy: deregistration forcefully closes WebSockets after delay

Twilio opens WebSocket ── WS Upgrade ──> ALB ──> ECS Task Connection: Upgrade Upgrade: websocket ALB passes upgrade through, connection pinned to this task 3. Audio streaming <──── bidirectional ────> Mulaw audio bytes flow continuously in both directions Connection stays open for entire call (minutes)

Hour 5-6 Route 53 + ACM (replaces ngrok)

  • ACM = free SSL certificates. Request for ivr.yourdomain.com, validate via DNS.
  • Route 53 = DNS. Create A record (alias) pointing to ALB.
  • After setup: Twilio webhook = https://ivr.yourdomain.com/voice/incoming
  • Twilio stream = wss://ivr.yourdomain.com/stream
  • No more ngrok — stable, production-grade public endpoint

Interview Answer — "How does Twilio connect?"
"ALB terminates TLS and handles WebSocket upgrade natively. When Twilio initiates a media stream, it sends an HTTP upgrade request. ALB passes this through to an ECS task, and the connection becomes a persistent bidirectional WebSocket for the duration of the call. I'd set idle timeout to 3600 seconds since phone calls can have long pauses. Route 53 provides DNS, ACM gives a free SSL cert — this completely replaces ngrok. Why ALB over NLB? Because we need Layer 7 for HTTP path routing and WebSocket upgrade — NLB is Layer 4 and can't do that."

RDS PostgreSQL

Conversation persistence — managed database

Hour 1-2 RDS Basics

  • RDS = managed PostgreSQL. AWS handles patching, backups, replication.
  • Multi-AZ: primary in AZ-a, synchronous standby in AZ-b. Auto-failover ~60s.
  • You connect to a single endpoint — RDS routes to active primary automatically.
  • Instance: db.r6g.large (2 vCPU, 16 GB) for production.
  • Storage: gp3 SSD, 50 GB with auto-scaling to 200 GB.
  • pgvector extension supported natively — for FAQ embeddings.

Hour 3-4 RDS Proxy (Critical for ECS)

  • PostgreSQL has hard limit on connections (~100-200 default)
  • Each ECS task opens ~10 connections. Scale from 2->6 tasks = 60 connections.
  • During deploy, old + new tasks both connect = double connections
  • RDS Proxy sits between ECS and RDS, multiplexes many app connections into few DB connections
  • Also handles failover transparently and supports IAM authentication

Hour 5-6 Backups & Security

  • Automated backups: daily snapshot, 7-day retention
  • Point-in-time recovery: restore to any second within retention window
  • Encryption at rest (KMS) and in transit (SSL)
  • RDS in private subnet, SG allows only ECS tasks on port 5432
Interview Answer — "Database strategy?"
"RDS PostgreSQL 16 with Multi-AZ for automatic failover. RDS Proxy in front because ECS auto-scaling causes connection spikes — during a rolling deployment, both old and new tasks connect simultaneously. RDS Proxy multiplexes these into a small pool. pgvector is supported natively for our FAQ embeddings. The DB sits in a private subnet, accessible only from ECS tasks via security group rules."

Hour 7-8 Rolling Deploy Mechanics

STEP 1
New task definition registered with new image tag
STEP 2
ECS launches new task (new version)
STEP 3
ALB health check passes on new task
STEP 4
ECS starts draining old task: ALB stops sending NEW connections. Existing WebSocket connections stay open.
STEP 5
After deregistration delay (300s), force-close remaining connections
STEP 6
Old task stopped. Repeat for next task.
Interview Answer — "Deployment strategy?"
"GitHub Actions builds the Docker image, pushes to ECR, then updates the ECS service with the new task definition. ECS does a rolling deployment — launches a new task, waits for ALB health checks to pass, then drains the old task. The 300-second deregistration delay is critical — active WebSocket connections for ongoing phone calls need time to complete naturally. The deploy waits for service stability before marking success. ECS circuit breaker auto-rolls back if new tasks keep failing health checks."

Hour 4-5 High Availability

  • Multi-AZ everything: ECS tasks, RDS, ElastiCache — all across 2 AZs
  • AZ failure scenario: ALB stops routing to failed AZ. ECS launches replacement tasks in healthy AZ. RDS fails over ~60s. Active calls in failed AZ are lost (callers redial).
  • RTO (Recovery Time): ~2 minutes
  • RPO (Recovery Point): 0 (synchronous RDS replication)

Hour 6-8 Graceful Shutdown (SIGTERM)

  • ECS sends SIGTERM when stopping a task (deploy, scale-in)
  • You have stopTimeout seconds (set to 120) before SIGKILL
  • App must: stop accepting new calls, drain active calls, return 503 on health check
import signal, asyncio active_calls: set[str] = set() shutting_down = False def handle_sigterm(signum, frame): global shutting_down shutting_down = True # Stop accepting new WebSocket connections # Wait for active_calls to drain signal.signal(signal.SIGTERM, handle_sigterm) # In /stream endpoint: async def media_stream(websocket): if shutting_down: await websocket.close(code=1001) # Going Away return active_calls.add(call_sid) try: await handler.run() finally: active_calls.discard(call_sid) # Health check returns 503 when draining: @app.get("/health") async def health(): if shutting_down: return JSONResponse({"status": "draining"}, status_code=503) return {"status": "ok"}
Interview Answer — "How do you scale and handle failures?"
"Auto-scaling on CPU with 60% target. Min 2 tasks across 2 AZs, max 6 for burst. The tricky part is scale-in — I use ECS scale-in protection: when a task handles active calls, it marks itself protected. On SIGTERM during deployments, the app stops accepting new connections, returns 503 on health checks so ALB drains it, and waits for active calls to complete. The stop timeout is 120 seconds. Between ALB deregistration delay and the SIGTERM handler, active calls finish naturally."

Cost Optimization + Security

Interview favorites: "how would you reduce cost?" and "how do you secure it?"

Hour 1-3 Cost Optimization Strategies

  • Fargate Spot for non-critical services (MLflow) — 70% cheaper
  • Scheduled scaling: if calls are business-hours only, min=0 at night — saves ~50% compute
  • RDS Reserved Instances: 1-year commit = 40% savings
  • NAT Gateway alternative: VPC endpoints for AWS services ($45/mo saving)
  • Log retention: 30 days, not forever
  • ECR lifecycle: auto-delete images older than 30 days

Hour 4-6 Security Best Practices

  • No secrets in code or Docker image — all from Secrets Manager
  • IAM least privilege — task role has only needed permissions
  • Private subnets — app and DB not publicly accessible
  • TLS everywhere: ALB (ACM), ECS->RDS (require SSL), ECS->Redis (in-transit encryption)
  • RDS encryption at rest — KMS managed key
  • ECR image scanning — scan for CVEs on push
  • WAF on ALB (optional) — rate limiting, block known bad IPs

Hour 7-8 Security Interview Scenarios

Q: How do you handle API key rotation? >
Secrets Manager supports automatic rotation. When a secret rotates, ECS tasks pick up the new value on next deployment or restart. For zero-downtime rotation, the app can fetch secrets at runtime with SDK caching.
Q: What if someone gets access to your container? >
Task role limits blast radius — it can only access CloudWatch and S3, not other services. Container runs in a private subnet with no inbound internet. DB credentials are fetched from Secrets Manager, not baked into the image. VPC Flow Logs show unusual outbound traffic.
Q: How do you prevent unauthorized access to the IVR endpoints? >
Twilio signs webhook requests with X-Twilio-Signature. The app validates this signature to ensure requests come from Twilio, not attackers. WebSocket stream uses a shared secret token in the URL query parameter. ALB only accepts HTTPS (443), HTTP (80) redirects to HTTPS.

Hour 4-8 Mock Interview Q&A

Click each question to reveal the answer. Practice answering OUT LOUD before clicking.

1. Walk me through the architecture >
Use the architecture diagram. Start from Twilio, go through Route 53, ALB, ECS Fargate, then explain data layer (RDS, Redis), security (Secrets Manager, IAM), and observability (CloudWatch). Mention external APIs going through NAT Gateway.
2. Why ECS Fargate over Lambda? >
Lambda has 15-min max timeout, no WebSocket support, and cold starts kill real-time audio latency. IVR calls need persistent connections for the entire duration. Fargate gives you long-running containers without managing EC2.
3. Why ALB over NLB? >
ALB is Layer 7 — understands HTTP, can do path-based routing (/stream vs /voice/*), and handles WebSocket upgrade. NLB is Layer 4 (TCP) and can't distinguish between HTTP paths or handle the upgrade protocol.
4. How do you deploy without dropping calls? >
Rolling deploy: replace one task at a time. ALB deregistration delay (300s) lets active WebSocket connections finish. App handles SIGTERM by stopping new call acceptance and returning 503 on health checks. ECS circuit breaker auto-rolls back if new tasks fail.
5. How do you handle an AZ failure? >
Multi-AZ everything. ALB stops routing to failed AZ. ECS launches replacement tasks in healthy AZ. RDS fails over to standby (~60s). Active calls in failed AZ are lost — callers redial. RTO ~2 minutes, RPO 0 (synchronous replication).
6. How do you scale to 100 concurrent calls? >
~50 calls per task (CPU-bound: each call runs STT + LLM + TTS streams). Auto-scale on CPU target 60%. Min 2, max 6 tasks. Scale-in protection prevents killing tasks with active calls. Custom metric active_calls_per_task as secondary trigger.
7. How do you handle database connection spikes during deploy? >
RDS Proxy. During rolling deploy, old + new tasks both have connection pools open. RDS Proxy multiplexes many app connections into few DB connections, preventing PostgreSQL max_connections exhaustion. Also handles failover transparently.
8. What's the cost and how would you optimize it? >
~$665/mo on-demand. Optimize: scheduled scaling (min=0 at night) saves 50% compute. RDS Reserved 1yr saves 40%. Fargate Spot for non-critical services. Log retention 30 days. NAT Gateway per AZ (not shared). Down to ~$450/mo.
9. Why not use Bedrock instead of Groq? >
Could use Bedrock for Llama or Claude. Advantage: stays within AWS (lower latency, simpler billing, no NAT Gateway needed for LLM calls). Trade-off: Groq has faster inference speed for Llama specifically. Bedrock is a valid alternative — it's an architectural decision based on latency vs simplicity.
10. What's the single point of failure? >
NAT Gateway — if it dies, no outbound API calls (Groq, Deepgram, ElevenLabs all fail). Mitigate by deploying NAT Gateway in each AZ. External APIs themselves are SPOFs but outside our control — mitigate with timeouts, circuit breakers, and fallback responses.
11. How do you trace a single call through the system? >
Every log line includes call_sid (structured JSON via structlog). CloudWatch Log Insights: filter by call_sid to see the complete journey — from WebSocket connect through auth, intent handling, every STT transcript, LLM response, TTS generation, to disconnect. X-Ray tracing optional for latency breakdown.
12. How do you handle a bad deployment? >
ECS deployment circuit breaker. If new tasks keep failing health checks (configurable threshold), ECS automatically rolls back to the previous working task definition. No manual intervention needed. The deploy GitHub Action also waits for service stability — if it times out, the pipeline fails and alerts the team.
13. Why Redis for session state instead of DynamoDB? >
Sub-millisecond reads for real-time audio pipeline. DynamoDB single-digit ms is fine for most apps but Redis is simpler for key-value with TTL, and we already use it locally. DynamoDB would be valid too — trade-off is managed scaling (DynamoDB) vs raw speed (Redis).
14. Walk me through what happens when a caller speaks >
Twilio captures mulaw audio from the phone. Sends it over WebSocket (through ALB) to our ECS task. Task forwards audio bytes to Deepgram's streaming STT API. Deepgram returns partial + final transcripts. Final transcript goes to LangGraph running on Groq (Llama 3.3 70B) for intent detection and response generation. Response text goes to ElevenLabs streaming TTS API. ElevenLabs returns mulaw audio chunks. We stream those back through the WebSocket to Twilio, which plays them to the caller. All of this happens in real-time — total latency target is under 2 seconds.
