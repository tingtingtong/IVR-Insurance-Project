1. Overview

US Insurance Company (UIC) operates an Avaya PBX as its primary telephony platform, handling all inbound and outbound calls across the organization. The AI-powered IVR system augments this existing infrastructure by providing intelligent, conversational self-service capabilities for policyholders.

When callers reach the main Avaya IVR menu, option 3 routes them to the AI IVR. This routing is accomplished via a SIP trunk between the Avaya PBX and Twilio Elastic SIP Trunking, which bridges the call into the AWS-hosted AI IVR application running on ECS behind an Application Load Balancer (ALB).

Key Concept: The Avaya PBX remains the front door for all calls. The AI IVR is a specialized backend reached via SIP trunk, not a replacement for the Avaya system.

Why This Approach?

  • Minimal disruption — existing Avaya dial plans, queues, and agent workflows remain unchanged
  • Incremental rollout — only option 3 traffic flows to the AI IVR; other options stay on Avaya
  • Bidirectional — calls can escalate back from AI IVR to Avaya agent queues with full context
  • Shared authentication — caller identity verified in Avaya can be passed to AI IVR via SIP headers

Step-by-Step Flow

  1. Caller dials UIC main number — PSTN routes to Avaya PBX
  2. Avaya IVR menu plays — caller selects option 3 for AI-assisted service
  3. Avaya sends SIP INVITE — routed via configured SIP trunk to Twilio's SIP URI, including UUI headers with caller context
  4. Twilio receives the SIP INVITE — triggers a TwiML webhook (HTTP POST) to the configured ALB endpoint
  5. ALB forwards to ECS — the FastAPI application processes the webhook, returns TwiML with <Connect><Stream> to establish a WebSocket media stream
  6. Bidirectional audio streaming — Twilio streams audio over WebSocket; the AI IVR processes speech via STT, runs LangGraph agent logic, and returns TTS audio

4. Context Passing (UUI Headers)

Avaya supports User-to-User Information (UUI) headers in SIP signaling, defined in RFC 7433. These headers allow the Avaya PBX to pass caller context to the AI IVR without requiring the caller to re-identify themselves.

UUI Data Payload

The UUI header carries a semicolon-delimited string with the following fields:

FieldDescriptionExample
aniCaller's ANI (phone number)+13175551234
acctAccount/policy number (if entered)POL-9876543
authAuthentication status from Avaya IVRverified / none
pathIVR menu path takenmain>3
cidAvaya call ID for correlationAVY-20260903-00142

SIP INVITE Example

INVITE sip:+18005551234@uic-ivr.pstn.twilio.com SIP/2.0
Via: SIP/2.0/TLS avaya-sbc.uic.com:5061;branch=z9hG4bK776
From: <sip:+13175551234@avaya-sbc.uic.com>;tag=1928301
To: <sip:+18005551234@uic-ivr.pstn.twilio.com>
Call-ID: a84b4c76e66710@avaya-cm.uic.com
User-to-User: ani=+13175551234;acct=POL-9876543;auth=verified;path=main>3;cid=AVY-20260903-00142;encoding=ascii
Contact: <sip:avaya-sbc.uic.com:5061;transport=tls>
Content-Type: application/sdp

Twilio Webhook Forwarding

Twilio forwards SIP headers as custom parameters in the webhook POST body. UUI data appears as SipHeader_User-to-User or via Twilio's X- header passthrough:

FastAPI Extraction Code

from fastapi import Request
from urllib.parse import unquote

def extract_uui_context(request_form: dict) -> dict:
    """
    Extract User-to-User Information from Twilio webhook parameters.
    Twilio passes SIP headers as form fields prefixed with 'SipHeader_'.
    """
    context = {
        "ani": request_form.get("From", ""),
        "account_number": None,
        "pre_authenticated": False,
        "ivr_path": None,
        "avaya_call_id": None,
    }

    # Extract UUI header from Twilio's SIP header passthrough
    uui_raw = request_form.get("SipHeader_User-To-User", "")
    if not uui_raw:
        uui_raw = request_form.get("SipHeader_X-UUI", "")

    if uui_raw:
        uui_decoded = unquote(uui_raw)
        # Parse semicolon-delimited fields
        for pair in uui_decoded.split(";"):
            if "=" in pair:
                key, value = pair.split("=", 1)
                key = key.strip().lower()
                if key == "acct":
                    context["account_number"] = value.strip()
                elif key == "auth":
                    context["pre_authenticated"] = value.strip() == "verified"
                elif key == "path":
                    context["ivr_path"] = value.strip()
                elif key == "cid":
                    context["avaya_call_id"] = value.strip()

    return context


# Usage in the /api/twilio/voice endpoint
@app.post("/api/twilio/voice")
async def handle_incoming_call(request: Request):
    form = await request.form()
    uui_context = extract_uui_context(dict(form))

    # Store context in Redis for the session
    call_sid = form.get("CallSid")
    await redis.hset(f"call:{call_sid}", mapping={
        "ani": uui_context["ani"],
        "account_number": uui_context["account_number"] or "",
        "pre_authenticated": str(uui_context["pre_authenticated"]),
        "avaya_call_id": uui_context["avaya_call_id"] or "",
    })

    # If pre-authenticated, skip auth flow in LangGraph
    if uui_context["pre_authenticated"]:
        # Route directly to intent handling
        ...
Tip: Always validate and sanitize UUI header values before use. Treat them as untrusted input — see the Security section for sanitization guidance.

5. Authentication Flow Integration

The AI IVR's authentication flow adapts based on whether the caller was already verified by the Avaya IVR before being routed to option 3.

Decision Flow


  Caller arrives at AI IVR
          |
          v
  +-------------------+
  | UUI auth=verified?|
  +-------------------+
       |           |
      YES          NO
       |           |
       v           v
  Skip auth    Check ANI
  Go to        (caller's phone #)
  intent       against policy DB
  handling          |
               +----+----+
               |Found?   |
               v         v
             YES        NO
              |          |
         Ask DOB      Ask phone #
         or name      + DOB or name
              |          |
              v          v
         2-PII match verified?
              |
         +----+----+
         |         |
        YES       NO (3 retries)
         |         |
    Authenticated  Route to agent

Pre-Authentication via UUI

When auth=verified is present in the UUI header, the AI IVR trusts that the Avaya system has already performed identity verification. The caller proceeds directly to intent handling (e.g., "How can I help you today?"). The account number from acct= is pre-loaded into the session.

Fresh Authentication

When no pre-authentication exists (auth=none or UUI absent):

  1. ANI Check — the system first checks the caller's phone number (ANI) against the policy database
  2. If ANI matches — ask for one additional PII factor (date of birth or last name)
  3. If ANI does not match — ask caller to provide their phone number or policy number, then verify with DOB or name
  4. 2-PII requirement — always requires two matching pieces of identifying information (phone+DOB, phone+name, policy+DOB, or policy+name)

Session State in Redis

Authentication state is stored in Redis keyed by Twilio CallSid. This enables warm transfer context persistence — if the call is escalated back to an Avaya agent, the agent's screen pop can query the same Redis store to see authentication status and conversation history. 

# Redis session structure
call:{CallSid}:
  ani: "+13175551234"
  account_number: "POL-9876543"
  authenticated: "true"
  auth_method: "uui_passthrough"   # or "ani+dob", "policy+name"
  avaya_call_id: "AVY-20260903-00142"
  intent: "billing_inquiry"
  conversation_summary: "Caller asked about premium payment due date..."

6. Escalation Back to Avaya

When the AI IVR determines that a live agent is needed (complex inquiry, caller frustration, or explicit request), the call is transferred back to an Avaya agent queue with full context.

Transfer Mechanism

The AI IVR uses Twilio's <Dial> verb with a SIP URI pointing back to the Avaya PBX. Conversation context is passed via custom SIP headers: 

# TwiML response for agent escalation
<Response>
  <Say>Let me connect you with a specialist who can help further.</Say>
  <Dial callerId="+13175551234">
    <Sip>
      sip:agent-queue-billing@avaya-sbc.uic.com:5061;transport=tls
      ?X-UIC-CallSid=CA1234567890abcdef
      &X-UIC-Intent=billing_inquiry
      &X-UIC-Auth=verified
      &X-UIC-Account=POL-9876543
      &X-UIC-Summary=Caller+asked+about+premium+due+date
    </Sip>
  </Dial>
</Response>

FastAPI Escalation Handler

from twilio.twiml.voice_response import VoiceResponse, Dial

async def escalate_to_agent(call_sid: str, queue: str = "general"):
    """Generate TwiML to transfer call back to Avaya agent queue."""
    # Retrieve session context from Redis
    session = await redis.hgetall(f"call:{call_sid}")

    response = VoiceResponse()
    response.say("Let me connect you with a specialist who can help further.")

    dial = Dial(caller_id=session.get("ani", ""))
    sip_uri = (
        f"sip:agent-queue-{queue}@avaya-sbc.uic.com:5061;transport=tls"
        f"?X-UIC-CallSid={call_sid}"
        f"&X-UIC-Intent={session.get('intent', 'unknown')}"
        f"&X-UIC-Auth={'verified' if session.get('authenticated') == 'true' else 'none'}"
        f"&X-UIC-Account={session.get('account_number', '')}"
    )
    dial.sip(sip_uri)
    response.append(dial)

    return str(response)

Agent Screen Pop

When the call arrives at the Avaya agent desktop, the CRM system (or CTI middleware) reads the custom SIP headers and performs an API call to retrieve the full conversation context:

  1. Avaya CTI connector extracts X-UIC-CallSid from inbound SIP INVITE
  2. CRM queries GET /api/session/{CallSid} on the AI IVR API
  3. Returns: authentication status, caller intent, conversation transcript, account details
  4. Agent sees full context in a screen pop before picking up the call

NAT and Codec Handling

Twilio handles NAT traversal transparently — the Avaya SBC does not need to worry about NAT for the Twilio leg. Twilio also handles codec transcoding if needed, though configuring Avaya to offer G.711 PCMU first avoids any transcoding latency.

Note: The ALB currently receives HTTPS webhooks from Twilio. Ensure a valid TLS certificate is configured on the ALB. Self-signed certificates will cause Twilio webhook delivery failures.

8. High Availability Considerations

Failover Behavior

If the AI IVR becomes completely unavailable (all ECS tasks down, ALB health checks failing):

  1. Twilio receives no response or an error from the webhook URL
  2. Twilio falls back to the configured fallback URL which returns a simple TwiML response
  3. Fallback TwiML plays an apology message and routes the caller back to Avaya via SIP REFER
  4. Avaya receives the call back and routes to the traditional IVR or agent queue
# Twilio Fallback TwiML (served from S3 or separate endpoint)
<Response>
  <Say>We're sorry, our automated assistant is temporarily unavailable.
       Please hold while we connect you to a representative.</Say>
  <Dial>
    <Sip>sip:agent-queue-general@avaya-sbc.uic.com:5061;transport=tls</Sip>
  </Dial>
</Response>
Tip: Host the fallback TwiML on a separate, highly reliable endpoint (e.g., an S3 static website or Twilio TwiML Bin) so it remains available even during an AWS region outage.

9. Security

Layered Security Model

LayerMechanismDetails
SIP Authentication Critical IP ACL + Credentials Twilio only accepts SIP INVITEs from whitelisted Avaya SBC IPs; optional digest authentication
SIP Signaling Encryption TLS (SIPS) SIP signaling over TLS on port 5061; prevents eavesdropping on call setup
Media Encryption SRTP Audio streams encrypted with SRTP; configured as "best-effort" on Avaya for compatibility
Webhook Security Twilio Request Validation Every webhook from Twilio is validated using the X-Twilio-Signature header and auth token
UUI Sanitization Critical Input Validation All UUI header values are validated, length-limited, and sanitized before use

Twilio Request Validation

from twilio.request_validator import RequestValidator

TWILIO_AUTH_TOKEN = os.environ["TWILIO_AUTH_TOKEN"]
validator = RequestValidator(TWILIO_AUTH_TOKEN)

@app.middleware("http")
async def validate_twilio_request(request: Request, call_next):
    if request.url.path.startswith("/api/twilio/"):
        signature = request.headers.get("X-Twilio-Signature", "")
        form = await request.form()
        url = str(request.url).replace("http://", "https://")

        if not validator.validate(url, dict(form), signature):
            return JSONResponse(status_code=403, content={"error": "Invalid signature"})

    return await call_next(request)

UUI Header Sanitization

import re

ALLOWED_UUI_FIELDS = {"ani", "acct", "auth", "path", "cid"}
MAX_FIELD_LENGTH = 64

def sanitize_uui(uui_raw: str) -> dict:
    """Sanitize UUI header to prevent injection attacks."""
    sanitized = {}
    for pair in uui_raw.split(";"):
        if "=" not in pair:
            continue
        key, value = pair.split("=", 1)
        key = key.strip().lower()

        # Only accept known fields
        if key not in ALLOWED_UUI_FIELDS:
            continue

        # Length limit
        value = value.strip()[:MAX_FIELD_LENGTH]

        # Remove any potentially dangerous characters
        value = re.sub(r'[^\w\-\+\.\>\@]', '', value)

        sanitized[key] = value

    return sanitized
Warning: Never trust UUI headers for authorization decisions without additional verification. A compromised or misconfigured SIP trunk could inject false auth=verified values. Consider adding an HMAC signature to the UUI payload that the AI IVR can verify.

10. Implementation Phases

The Avaya integration follows a phased rollout to minimize risk and validate each layer independently:

Phase 1: SIP Trunk Setup + Basic Routing (1-2 weeks)
  • Configure SIP trunk between Avaya SBC and Twilio Elastic SIP Trunking
  • Set up IP ACL and credential authentication on Twilio
  • Configure Avaya dial plan to route option 3 to the SIP trunk
  • Validate end-to-end call flow with test calls
  • Verify codec negotiation (G.711 PCMU preferred)
  • Test firewall rules for SIP and RTP traffic

Milestone: Test call from Avaya reaches AI IVR and gets a response

Phase 2: Context Passing via UUI Headers (1 week)
  • Configure Avaya to populate UUI headers with caller ANI, account number, and auth status
  • Update AI IVR FastAPI endpoint to extract and parse UUI headers from Twilio webhook
  • Implement UUI sanitization and validation
  • Test pre-authenticated flow (skip auth when auth=verified)
  • Test fresh auth flow (ANI check + DOB/name verification)

Milestone: Pre-authenticated callers skip the auth flow in AI IVR

Phase 3: Bidirectional Transfers with Context (2 weeks)
  • Implement escalation TwiML to transfer calls back to Avaya agent queues via SIP
  • Pass conversation context (intent, summary, auth status) in custom SIP headers
  • Configure Avaya to accept inbound SIP calls from Twilio with context headers
  • Set up skill-based routing in Avaya based on AI-determined intent
  • Test end-to-end escalation flow including context preservation

Milestone: Agent receives call with AI conversation context visible

Phase 4: Agent Screen Pop Integration (2 weeks)
  • Build REST API endpoint for CRM to query conversation session data
  • Integrate Avaya CTI connector to extract custom SIP headers on agent delivery
  • Configure CRM screen pop to display: caller identity, intent, conversation transcript, and suggested actions
  • Load testing and performance tuning for Redis session lookup latency
  • UAT with agent teams and production pilot

Milestone: Full production deployment with agent screen pop

12. Key Takeaways

  1. Avaya remains the front door — the AI IVR is accessed via option 3 on the existing Avaya IVR menu, requiring no changes to the caller experience for other menu options.
  2. SIP trunk is the bridge — Twilio Elastic SIP Trunking connects Avaya to the AWS-hosted AI IVR with minimal infrastructure changes. G.711 PCMU is the required codec.
  3. UUI headers eliminate redundant authentication — callers verified by Avaya skip re-authentication in the AI IVR, reducing handle time and improving caller experience.
  4. Bidirectional transfers preserve context — escalation back to Avaya agent queues includes conversation summary, caller intent, and authentication status via SIP headers and Redis-backed session state.
  5. Security is layered — IP ACLs, TLS, SRTP, webhook validation, and UUI sanitization work together to protect the integration at every layer.
  6. Failover is graceful — if the AI IVR is unavailable, Twilio's fallback URL routes callers back to Avaya's traditional IVR or agent queue.
  7. Phased rollout reduces risk — four phases over approximately 6-7 weeks, from basic SIP trunk connectivity through full agent screen pop integration.
