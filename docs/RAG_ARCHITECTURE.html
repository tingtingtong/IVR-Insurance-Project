3. Async PGVector Fix

Problem

# CURRENT CODE -- services/rag.py line 34
async def search_knowledge(query: str, k: int = 3) -> str:
    store = _get_store()
    docs = store.similarity_search(query, k=k)  # BLOCKING CALL

PGVector.similarity_search() uses synchronous SQLAlchemy under the hood. When called inside async def, it blocks the Python event loop. In our IVR system this means:

  • All active Twilio WebSocket streams freeze (callers hear silence)
  • Deepgram STT transcription buffers overflow
  • ElevenLabs TTS audio delivery stalls
  • Other HTTP handlers (dashboard, health checks) queue up

A pgvector query takes 50-200ms. During that time, every concurrent call is frozen.

Solution: asyncio.run_in_executor()

# TARGET CODE
async def search_knowledge(query: str, k: int = 3) -> str:
    store = _get_store()
    loop = asyncio.get_event_loop()

    # Offload blocking SQLAlchemy call to thread pool
    docs = await loop.run_in_executor(
        None,  # default ThreadPoolExecutor
        lambda: store.similarity_search(query, k=k)
    )

Options evaluated

OptionProsCons
run_in_executor chosen Works with current PGVector class, no dependency changes, battle-tested Thread pool overhead (~1ms), not true async IO
asimilarity_search() True async IO, no thread overhead langchain_community.PGVector does not implement async methods as of v0.3.14
Migrate to langchain_postgres Native async, actively maintained Breaking change: different constructor, filter syntax, requires re-seeding
Decision: Use run_in_executor for now. Solves blocking with zero migration risk. Migrate to langchain_postgres native async in a future sprint.

Thread pool sizing

Default ThreadPoolExecutor creates min(32, os.cpu_count() + 4) threads. Peak concurrent FAQ queries: ~10-20 (one per active call). Each thread holds a connection briefly (~100ms). Default pool is sufficient.

For production, use a dedicated bounded executor:

from concurrent.futures import ThreadPoolExecutor
_rag_executor = ThreadPoolExecutor(max_workers=10, thread_name_prefix="rag")

4. Redis Caching Layer

Why cache RAG results?

MetricWithout CacheWith Cache (hit)
OpenAI Embedding API call1 per query0
PGVector DB query1 per query0
Re-ranking LLM callsk*3 per query0
Total latency400-800ms2-5ms
Cost per query~$0.00005$0

Cache design

Key:    cno:rag:<sha256(normalized_query + k + category)[:16]>
Value:  concatenated context string (the final reranked result)
TTL:    3600 seconds (1 hour)
Design ChoiceRationale
SHA256 for keysQueries can be long with special chars. SHA256 is deterministic and collision-resistant. 16-char prefix = 64 bits of entropy.
1-hour TTLKnowledge base changes infrequently (quarterly). 1 hour balances freshness with hit rate. Call clear_cache() on ingestion.
Cache final stringSimpler — one entry per query. Re-ranking is query-dependent, so caching pre-rerank docs doesn't help.

Graceful degradation

If Redis is unavailable: _get_redis() returns None, cache operations become no-ops, pipeline continues without caching. Matches existing pattern in services/session.py (falls back to fakeredis).

5. Metadata Filtering

Problem

Without filtering, "How do I change my beneficiary?" searches all chunks equally. Irrelevant chunks about ACH authorization or dividends consume top-k slots, reducing answer quality.

Solution: Category-based pre-filtering

Step 1: Detect category from query keywords
  "How do I change my beneficiary?" -> category = "beneficiaries"

Step 2: Pass filter to pgvector
  store.similarity_search(query, k=9, filter={"category": "beneficiaries"})

Step 3: If filtered results < k, fall back to unfiltered search

Why keyword matching instead of LLM-based category detection?

ApproachLatencyCostAccuracy
Keyword matching chosen<1ms$0~85%
LLM classification200-400ms~$0.00003~95%
Embedding similarity100-200ms~$0.00002~90%
Decision: Keyword matching. Runs in <1ms with zero cost. Fallback to unfiltered search handles the 15% miss rate.

6. Cross-Encoder Re-Ranking

Why re-rank?

StageMethodSpeedAccuracy
Bi-encoder (PGVector)Encodes query & docs independentlyFast: O(1) per docApproximate
Cross-encoder (re-rank)Encodes query & doc togetherSlow: O(n) scoringPrecise
CombinedBi-encoder retrieves 9 candidates, cross-encoder picks top 3Best of bothBest of both

Example: Re-ranking impact

Query: "What happens if I stop paying my premiums?"

RankWithout Re-ranking (raw cosine)With Re-ranking
1 "Your premium is the amount you pay to keep..." (0.82) "If you miss a premium payment your policy enters a 30-day grace period..." (9/10)
2 "Online and phone payments post within 24-48 hours..." (0.79) "A Lapsed policy means coverage has ended because premiums were not paid..." (8/10)
3 "Autopay automatically deducts your premium..." (0.77) "Your premium is the amount you pay to keep..." (7/10)

The re-ranker correctly identifies chunks about consequences of non-payment over chunks about what a premium is.

Implementation options compared

ApproachModelLatencyCostDeployment
LLM re-ranking chosen Groq Llama-3.1-8B~200ms (parallel)~$0.0001/queryNo extra infra
Sentence-transformersms-marco-MiniLM-L-6-v2~50ms (local)$0 (GPU)GPU instance, 400MB model
Cohere Rerank APIrerank-english-v3.0~150ms$0.002/queryThird-party dependency
BGE Rerankerbge-reranker-v2-m3~80ms (local)$0 (GPU)GPU instance, 1.2GB model
Decision: LLM re-ranking via Groq. Already have Groq connection. 8B model is fast enough. No additional infrastructure. For scale, migrate to self-hosted cross-encoder on SageMaker.

Re-ranking prompt

System: You are a relevance scorer. Reply with only a number 0-10.

User: Rate how relevant this text is to answering the question.
Question: {query}
Text: {chunk_text[:300]}
Reply with ONLY a number from 0 to 10.

All 9 candidates are scored concurrently with asyncio.gather(), reducing re-ranking from 9 x 200ms = 1.8s (sequential) to ~200ms (parallel).

8. Chunking Strategy

Why chunking matters

A 20-page PDF cannot be embedded as one vector. Chunks must: (1) fit the embedding window (512-1024 tokens), (2) preserve semantic coherence, (3) include overlap for boundary context.

Parameters chosen

ParameterValueRationale
SplitterRecursiveCharacterTextSplitterTries \n\n → \n → . → in order. Preserves paragraph boundaries first
Chunk size500 characters (~100-125 tokens)Existing manual chunks average 200-350 chars. 500 gives room for complete thoughts
Chunk overlap50 characters (~10-12 tokens)10% overlap for continuity. >20% wastes storage with near-duplicates
Length functionlen (character count)Token-based adds ~5ms/chunk. Character count is a good proxy for English

Splitter comparison

SplitterBehaviorBest ForWhy Not
RecursiveCharacterTextSplitter chosenHierarchical separatorsGeneral text, mixed formats—
CharacterTextSplitterSingle separator onlyUniform textSplits mid-paragraph
TokenTextSplitterExact token countToken-critical appsIgnores semantic boundaries
MarkdownHeaderTextSplitterSplits on #, ##Structured markdownOnly works for Markdown
SemanticChunkerGroups by embedding similarityResearch documentsExtremely slow, high cost

Why text-embedding-3-small?

13. Production Checklist

  • Async fix: All pgvector calls use run_in_executor
  • Redis caching: Active with 1hr TTL, graceful fallback
  • Metadata filtering: Category detection + filtered search
  • Re-ranking: LLM re-ranker with parallel scoring
  • Document pipeline: Supports PDF, URL, text, CSV
  • HNSW index: Created when chunk count exceeds 500
  • Connection pooling: SQLAlchemy pool or PgBouncer
  • Monitoring: Latency, cache hit rate, quality logged
  • Cache invalidation: clear_cache() after every ingestion
  • Evaluation: All 20+ test queries score ≥ 0.80 faithfulness
  • Load test: 50 concurrent RAG queries < 1s p95
  • Graceful degradation: RAG failure → canned response
