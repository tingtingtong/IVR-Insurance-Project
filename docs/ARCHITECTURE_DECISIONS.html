Architecture Decisions

#1

LangGraph for Orchestration (not LangChain)

Stateful graph with nodes/edges instead of a simple chain

Decision Use LangGraph's stateful directed graph to orchestrate the entire call flow.

Why IVR calls are multi-turn, multi-step workflows: authentication, intent routing, service fulfillment, and back again. A graph models this naturally — nodes are intent handlers, edges are transitions between conversational states.

  • LangChain's sequential chains cannot handle branching, loops, or state persistence across turns.
  • LangGraph provides built-in checkpointing, conditional edges, and a clear visual model of every possible call path.
  • Each node is independently testable. Adding a new intent means adding a node and edges — no refactoring of the chain.
  • The graph state object travels with the call, accumulating context (auth status, caller info, current intent) at every step.
#2

Dual LLM Strategy (Router vs Service Nodes)

Lightweight model for intent routing, larger model for service nodes

Decision Run two different LLM tiers: a fast, inexpensive model for intent classification and a more capable model for generating service responses.

Why The router runs on every single caller utterance — it needs to be fast and cheap. Service nodes (billing lookup, claims status, policy changes) need deeper reasoning and more nuanced language generation.

  • Router model (e.g., Groq/Llama or Bedrock Nova Micro): sub-200ms latency, handles intent classification and slot extraction.
  • Service model (e.g., larger Llama variant or Claude): handles complex responses, multi-step reasoning, and policy-specific language.
  • This separation gives sub-second routing with high-quality responses where it actually matters to the caller experience.
  • Cost savings are significant: routing is ~90% of LLM calls but uses the cheapest tier.
#3

Streaming Pipeline (WebSocket, not REST)

End-to-end streaming from caller voice to IVR response

Decision Build the entire audio pipeline on WebSockets: Twilio Media Streams to Deepgram STT (streaming) to LangGraph to ElevenLabs TTS (streaming) back to Twilio.

Why Latency is the single most critical metric in voice. REST-based approaches require waiting for the full utterance to finish, then full transcription, then full LLM response, then full TTS audio. Each "wait for full" adds hundreds of milliseconds.

  • Streaming STT provides words as they are spoken — the system can start processing before the caller finishes.
  • Streaming TTS sends audio chunks as they are generated — the caller hears the response begin in under a second.
  • Target response time: <1 second from end of caller speech to beginning of IVR response.
  • WebSocket connections are persistent for the call duration, eliminating per-request connection overhead.
#4

Sidecar Pattern for Mock API

Mock backend API runs as a sidecar container in the same ECS task

Decision Deploy a lightweight mock API container alongside the main IVR container within the same ECS task definition.

Why The IVR application calls a backend API for policy lookup, payment processing, claims status, and other operations. In development and demo environments, a mock sidecar running on localhost:8001 avoids any dependency on the real backend systems.

  • Zero network latency — sidecar shares the same network namespace (localhost communication).
  • Same task definition for both containers, deployed and scaled together.
  • In production, the IVR simply points to the real backend API endpoint — no code changes, just an environment variable.
  • The mock API returns realistic test data, enabling full end-to-end demos without touching production systems.
#5

PostgreSQL for Both State and Vectors (not separate vector DB)

pgvector extension on the same RDS instance for RAG

Decision Use PostgreSQL with the pgvector extension for both relational data and vector similarity search, rather than running a separate vector database.

Why The FAQ knowledge base is relatively small — hundreds of documents, not millions. At this scale, pgvector performs comparably to dedicated vector databases like Pinecone or Weaviate.

  • One fewer service to provision, monitor, and pay for.
  • One fewer network connection to maintain and one fewer point of failure.
  • Relational queries and vector similarity search can be combined in a single query (e.g., filter by category, then rank by embedding similarity).
  • If the knowledge base grows to millions of documents, migration to a dedicated vector DB is straightforward — the embedding format is standard.
#6

Redis for Session State, Postgres for Checkpointing

Split state across two stores based on durability requirements

Decision Use Redis for ephemeral session data and PostgreSQL for durable LangGraph checkpoints.

Why Not all state has the same durability requirements. Active call session data (current node, turn count, TTS queue) is short-lived and accessed frequently. LangGraph checkpoints (full graph state snapshots) need to survive crashes and support call history analysis.

  • Redis: sub-millisecond reads, TTL-based automatic expiry for abandoned calls, perfect for hot session data.
  • PostgreSQL: ACID-compliant persistence, the LangGraph checkpointer saves state after each node transition for crash recovery.
  • If Redis goes down, the system falls back to an in-memory session store — calls in progress continue, just without cross-instance session sharing.
  • Call history in Postgres enables analytics: average call duration, most common intents, auth failure rates.
#7

ECS Fargate (not Lambda, not EC2)

Managed containers without server management

Decision Deploy on AWS ECS Fargate — not Lambda (serverless functions) and not EC2 (self-managed servers).

Why WebSocket connections are long-lived — they persist for the entire duration of a phone call (minutes to tens of minutes). This rules out Lambda, which has a 15-minute timeout and does not support WebSocket connections natively.

  • Lambda: 15-minute max execution, no WebSocket support, cold starts add latency — disqualified for voice.
  • EC2: full control but requires managing OS patches, scaling policies, instance types — overkill for a demo/MVP.
  • Fargate: container flexibility (run any runtime, any dependencies) without managing the underlying hosts.
  • Pay only for the vCPU and memory used while tasks are running. Scales to zero when no calls are active.
#8

ALB (not API Gateway)

Application Load Balancer for WebSocket support

Decision Use an Application Load Balancer in front of ECS tasks, not AWS API Gateway.

Why ALB natively supports the HTTP Upgrade mechanism required for WebSocket connections. API Gateway's WebSocket API uses a different routing model (route keys, $connect/$disconnect stages) that adds complexity and per-message billing.

  • ALB handles WebSocket upgrade transparently — no special configuration beyond enabling stickiness.
  • API Gateway WebSocket charges per message (send and receive), which adds up fast with streaming audio packets.
  • ALB integrates directly with ECS service discovery and health checks.
  • Simpler architecture: one ALB handles both the REST webhook endpoint (for Twilio call initiation) and the WebSocket endpoint (for media streaming).
#9

Barge-in with VAD

Voice Activity Detection for caller interruption

Decision Implement barge-in (caller interruption) using Voice Activity Detection on the incoming audio stream.

Why Callers should not have to wait for the IVR to finish speaking before they can respond. This is especially important for experienced callers who already know what they want — forcing them to listen to full prompts creates frustration.

  • VAD detects when the caller starts speaking during TTS playback.
  • Upon detection: TTS audio is immediately stopped, the partial utterance is captured, and the system processes the new input.
  • This is critical for a natural conversation feel — without it, the IVR feels like a traditional "press 1 for..." system.
  • Deepgram's streaming STT includes built-in endpointing and VAD, reducing implementation complexity.
#10

Auth Guard Pattern

Centralized auth gate in the graph, not per-node checks

Decision Implement a single auth_guard conditional edge in the LangGraph that runs before any service node, rather than duplicating auth checks inside every node.

Why Every service intent (billing, claims, policy changes) requires the caller to be authenticated. Scattering if not authenticated checks across a dozen nodes is error-prone — one missed check means an unauthenticated caller can access account data.

  • Single point of enforcement: the auth guard edge checks state.is_authenticated before routing to any protected node.
  • If not authenticated, the caller is redirected to the authentication flow, then returned to their original intent after success.
  • Adding new service nodes is safe by default — they are behind the auth guard automatically.
  • Auth requires 2 PII matches (phone + DOB, phone + name, policy + DOB, or policy + name). ANI (caller's phone number) is checked first.
#11

Terraform State in S3 (not local)

Remote state with S3 + DynamoDB locking

Decision Store Terraform state in an S3 bucket with DynamoDB-based state locking, rather than keeping terraform.tfstate on a local machine.

Why Remote state is required for CI/CD — GitHub Actions workflows need to run terraform apply and terraform destroy without access to a developer's local filesystem.

  • Local state ties infrastructure management to a single machine — loses the state file, lose track of all resources.
  • DynamoDB locking prevents concurrent terraform apply runs from corrupting state (e.g., two developers or two CI runs).
  • S3 versioning provides automatic backup of every state change — easy to roll back if an apply goes wrong.
  • Enables the full CI/CD pipeline: push to main triggers build, push image, terraform apply, ECS redeploy.
#12

ECR Outside Terraform

Container registry persists across infra destroy/apply cycles

Decision Create and manage the ECR (Elastic Container Registry) repository outside of the Terraform configuration, so it is not destroyed when running terraform destroy.

Why Docker images are expensive to build — the IVR image is approximately 1.13 GB and takes around 10 minutes to build. Destroying and recreating ECR on every infra cycle would require a full rebuild every time.

  • With ECR persisted: redeploy = terraform apply + ECS task restart, approximately 5 minutes total.
  • Without ECR persisted: redeploy = Docker build (10 min) + push (2 min) + terraform apply (5 min) = 17+ minutes.
  • ECR lifecycle policies handle cleanup of old/untagged images automatically.
  • The ECR repository is a one-time setup (aws ecr create-repository) that outlives all other infrastructure.
#13

Auto-Scaling at Every Layer

ECS tasks, RDS, and Redis scale independently based on load

Decision Implement auto-scaling at the compute layer (ECS) with three independent scaling policies, and make database/cache instance sizes configurable per environment.

Why A voice IVR has highly variable load — peak hours (9am-5pm) see 5-10x the traffic of off-peak. Fixed capacity either wastes money during quiet periods or drops calls during spikes.

  • ECS CPU scaling: Adds tasks when average CPU exceeds 60%. Audio processing (resampling, encoding) and LLM API serialization are CPU-bound.
  • ECS Memory scaling: Adds tasks when average memory exceeds 70%. Each concurrent call holds WebSocket buffers, audio queues, and graph state in memory.
  • ALB Request Count scaling: Adds tasks when active requests per target exceed 10. This directly tracks concurrent call count — the most meaningful metric for a voice system.
  • Scale-out cooldown: 60s — react quickly to traffic spikes. Scale-in cooldown: 120s — avoid flapping during natural call volume fluctuations.
  • RDS/Redis: Instance sizes are Terraform variables. Dev uses db.t4g.micro / cache.t4g.micro (~$15/month). Prod uses db.t4g.small / cache.t4g.small (~$30/month). Upgrade is a single variable change.
  • Capacity planning for 3,000 calls/day: ~375 calls/hour peak → ~24 concurrent calls → 5-8 ECS tasks (1 vCPU, 2GB each). Auto-scaler handles this automatically.
#14

Hybrid STT: Deepgram + OpenAI Realtime API

Switch STT engines mid-call based on data sensitivity and accuracy requirements

Decision Use Deepgram for general conversation and OpenAI Realtime API for sensitive PII collection (authentication, credit card numbers). The system dynamically switches between the two mid-call.

Why Deepgram excels at streaming conversational speech (fast, cheap, great endpointing), but structured data like phone numbers, dates of birth, policy numbers, and credit card numbers require higher accuracy. OpenAI Realtime API hears raw audio directly — no intermediate STT errors — and uses function calling to extract structured fields with high precision.

  • Normal flow: Twilio audio → Deepgram STT (streaming) → LangGraph → ElevenLabs TTS → Twilio. Fast, low-cost, great for open conversation.
  • PII collection flow: Twilio audio → OpenAI Realtime API (STT + LLM combined) → structured extraction → back to normal flow. Higher accuracy for digits and names.
  • Controlled via AUTH_MODE=realtime setting. When active, the WebSocket handler routes audio to OpenAI Realtime during authentication, then seamlessly switches back to Deepgram + LangGraph after auth completes.
  • OpenAI Realtime handles its own VAD, clarifications, and corrections in-context — the model can ask "Did you say 4-5-7 or 4-5-9?" without round-tripping through a separate LLM.
  • Cost trade-off: OpenAI Realtime is ~6x more expensive than Deepgram (~$0.06/min vs ~$0.01/min), but it's only active for ~30-60 seconds per call during PII collection. Total cost impact: negligible.
  • Extensible pattern: The same switching mechanism can be applied to any node that needs high-accuracy structured input — credit card numbers in the payment node, addresses in the contact update node, etc.
  • Security benefit: PII audio goes through a separate pipeline, making it easier to isolate, audit, and apply compliance controls (e.g., PCI DSS for payment card data).
#15

Avaya PBX Integration via SIP Trunk (not direct replacement)

Coexist with enterprise telephony rather than rip-and-replace

Decision Integrate the AI IVR as an extension of the existing Avaya PBX system via SIP trunk through Twilio, rather than replacing the entire PBX. Avaya IVR menu option 3 routes callers to the AI IVR while all other options remain on the traditional system.

Why Enterprise PBX replacement is a multi-year, high-risk project. By integrating via SIP trunk, we can deploy the AI IVR incrementally — starting with a single menu option — without disrupting existing call flows, agent queues, or compliance controls. The Avaya system continues to handle call routing, queue management, and agent distribution.

  • Call flow: Caller → Avaya PBX → IVR Menu → Option 3 → SIP Trunk → Twilio Elastic SIP Trunking → Webhook → ALB → ECS (AI IVR)
  • Context passing: Avaya sends User-to-User Information (UUI) headers in the SIP INVITE containing caller ANI, account number, and authentication status. Twilio forwards these as custom parameters in the webhook. The AI IVR extracts them to skip re-authentication when the caller is already verified.
  • Escalation back: When the AI IVR needs a live agent, it uses Twilio's <Dial> with a SIP URI back to an Avaya agent queue, passing conversation context (summary, intent, account info) via SIP headers. The agent gets a screen pop with the full conversation history.
  • Shared session state: Redis stores session data accessible by both the AI IVR and agent-facing tools, enabling warm transfers where the agent sees everything the AI discussed with the caller.
  • High availability: Dual SIP trunks (primary + failback). If the AI IVR is unavailable (ALB health check fails), Avaya falls back to the traditional IVR or routes directly to an agent queue — no caller is dropped.
  • Security: SIP trunk secured with IP ACL + credential authentication. TLS for SIP signaling (SIPS), SRTP for media encryption. UUI headers are sanitized to prevent injection attacks.
  • Phased rollout: Phase 1 — basic SIP trunk routing (1-2 weeks). Phase 2 — UUI context passing (1 week). Phase 3 — bidirectional transfers with context (2 weeks). Phase 4 — agent screen pop integration (2 weeks). Total: ~6-7 weeks.

Common Interview Questions

Question Key Point
"Why not use Amazon Connect?" Amazon Connect is a full CCaaS (Contact Center as a Service) — it provides less control over LLM integration, makes it harder to customize authentication flows, and creates vendor lock-in. Building on open components (Twilio + LangGraph + Deepgram) gives full control over every layer of the stack.
"How do you handle cold starts?" Fargate has no cold start problem like Lambda. ECS tasks are always running and ready to accept connections. STT and TTS WebSocket connections are established at call start, not at container start, so the first call is just as fast as the hundredth.
"How do you scale?" ECS auto-scaling based on CPU utilization and active connection count. The application is stateless (all state lives in Redis and PostgreSQL), so horizontal scaling works — add more tasks behind the ALB. Each task handles multiple concurrent calls.
"What about reliability?" Graceful fallbacks at every layer: PostgreSQL checkpointer falls back to in-memory if the database is unreachable. RAG retrieval falls back to canned FAQ responses. Groq (primary LLM) falls back to Bedrock as a backup provider. No single failure takes down the system.
"Security?" Twilio request signature validation on all webhooks. AWS Secrets Manager for all API keys (never in environment variables or code). VPC security groups restrict access — RDS and Redis have no public endpoints. All traffic is encrypted in transit (TLS/WSS).
"Why Groq over OpenAI for LLM?" Groq offers sub-200ms inference on Llama models — critical for voice latency where every millisecond counts. OpenAI's GPT models have higher latency (400-800ms typical). OpenAI is used only for generating embeddings (where latency is less critical, and quality matters more).
"Why ElevenLabs over Amazon Polly?" ElevenLabs provides significantly more natural-sounding voices with lower latency streaming. The voice quality difference is immediately noticeable to callers. Polly is cheaper per character but sounds more robotic, which undermines the "conversational AI" experience the IVR is designed to deliver.
"Why use two different STT engines?" Deepgram is optimized for fast, streaming conversational speech at low cost. But for structured data (phone numbers, DOB, credit card numbers), accuracy matters more than speed. OpenAI Realtime API processes raw audio with an LLM that can use function calling to extract exact digits — no intermediate transcription errors. The system switches dynamically mid-call: Deepgram for conversation, Realtime for PII collection, then back. Cost impact is minimal since Realtime is only active for ~30-60 seconds per call.
"How do you handle call failures mid-conversation?" The LangGraph checkpointer saves the full graph state after each node transition. On reconnect or retry, the graph can resume from the last successful checkpoint — the caller does not have to re-authenticate or repeat information. Redis session TTL (configurable, typically 30 minutes) handles automatic cleanup of abandoned calls.
"How does this integrate with an existing Avaya PBX?" Via SIP trunk through Twilio Elastic SIP Trunking. Avaya routes IVR option 3 to Twilio, which triggers a webhook to our ALB/ECS. Avaya passes caller context (ANI, auth status, account number) via UUI headers in the SIP INVITE, so the AI IVR can skip re-authentication. For escalation, the AI IVR transfers back to Avaya agent queues via SIP URI with conversation context. This coexistence model avoids PBX replacement risk and enables incremental rollout.
"What happens if the AI IVR goes down?" Avaya is configured with dual SIP trunks (primary + failback). If the ALB health check fails, Twilio returns an error on the SIP trunk. Avaya detects this and routes the call to the traditional IVR menu or directly to an agent queue. No caller is ever dropped — the fallback is seamless and automatic. ECS auto-scaling (min 2 tasks in prod) and multi-AZ ALB further reduce the probability of a complete outage.
"How do you handle warm transfers between AI and agents?" When escalation is needed, the AI IVR writes a conversation summary (intent, account info, what was discussed, unresolved issues) to Redis and passes a session ID via SIP headers back to Avaya. The agent's CRM pulls the conversation history from our API using that session ID, providing a screen pop with full context. The caller never has to repeat themselves — the agent sees the entire AI conversation before picking up.
