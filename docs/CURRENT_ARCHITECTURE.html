1 System Overview

What This System Is

The UIC IVR is an AI-powered conversational Interactive Voice Response system that replaces traditional menu-tree IVRs with a natural-language, streaming voice interface. Callers speak naturally rather than pressing "1 for policy information, 2 for payments." An LLM classifies intent in real time, a multi-turn authentication state machine verifies identity, and domain-specific service nodes handle each use case (policy lookup, payment, loan inquiry, beneficiary info, document requests, etc.).

What Makes It Different From Traditional IVR

  • No menu trees — callers state their intent in natural language at any point; the router node classifies it via LLM
  • Real-time streaming audio — bidirectional WebSocket audio between Twilio and the server; STT and TTS happen in parallel with sub-second latency
  • Barge-in support — WebRTC VAD detects when a caller starts speaking during a TTS response and immediately cancels playback
  • Hybrid STT strategy — Deepgram Nova-2 for general conversation; OpenAI Realtime API for authentication PII collection (higher accuracy on digits, dates, names)
  • Graph-based orchestration — LangGraph state machine with checkpointing, conditional routing, and auth guards rather than a monolithic conversation loop
  • RAG-grounded FAQ — insurance knowledge base in pgvector; answers are grounded in retrieved context, not hallucinated

End-to-End Call Flow Narrative

1. Caller dials UIC phone number (Twilio PSTN)
2. Twilio hits POST /webhook/voice → TwiML starts Media Stream to wss://server/stream
3. CallHandler._on_start() initializes Redis session, starts Deepgram STT connection
4. Greeting TTS plays: "Thank you for calling. How can I help you today?"
5. Caller speaks → mulaw audio streams through WebSocket → Deepgram transcribes
6. Final transcript fires _on_transcript() → _process_turn()
7. LangGraph graph.ainvoke():
     a. Router node classifies intent (e.g. "policy_info")
     b. Conditional edge routes to policy node
     c. Auth guard checks authentication — not authenticated yet
     d. Auth node runs: asks for phone number
     e. Returns tts_text + active_flow="policy"
8. TTS streams auth prompt to caller via ElevenLabs/OpenAI → mulaw → Twilio
9. Multi-turn auth loop: phone → party_search → DOB → name → 2-PII match
10. Auth complete → token acquired → caller persona identified
11. Service node executes: calls holding_inquiry API → LLM generates response
12. TTS speaks policy info: "Your policy is active. Premium is $45.00 monthly..."
13. "Is there anything else?" → caller says "no" → goodbye node → hangup

Why WebSocket Over REST for Voice

REST-based STT requires buffering the entire utterance, sending it, waiting for a response, then synthesizing TTS — adding 2-4 seconds of latency per turn. WebSocket streaming enables:

  • Continuous audio flow — no buffering delay; Deepgram processes audio as it arrives
  • Interim transcripts — partial results enable early processing (though currently only final transcripts trigger graph invocation)
  • Barge-in — impossible with REST since the server doesn't receive audio during TTS playback
  • Streaming TTS — first audio chunk reaches the caller ~200ms after TTS generation starts

Barge-In / VAD Implementation

The VADService uses webrtcvad at aggressiveness level 3 (most aggressive, best for noisy phone lines). It processes audio only while TTS is playing (self._speaking = True):

  1. Incoming mulaw bytes are converted to 16-bit PCM via audioop.ulaw2lin()
  2. PCM is buffered and split into 20ms frames (320 bytes at 8kHz 16-bit)
  3. Each frame is checked with vad.is_speech(frame, 8000)
  4. A counter tracks consecutive speech frames; 3 consecutive frames (60ms) triggers barge-in
  5. On barge-in: TTS task is cancelled, a "clear" event is sent to Twilio to flush its audio buffer
  6. VAD state resets when TTS finishes or barge-in fires

3 Hybrid STT Strategy

When Each STT Engine Is Used

Why Not Use Deepgram For Everything?

Deepgram excels at general conversational transcription but introduces errors on the exact data points that matter most during authentication:

  • Phone numbers: "5-5-5-1-2-3-4-5-6-7" may transcribe as "555 1234567" or "5,551,234,567" — requires post-processing normalization that can fail
  • Dates of birth: "March 15th, 1982" may become "March 15 1982" or "3/15/82" — inconsistent formats need regex parsing
  • Names: Uncommon surnames are frequently misheard
  • Policy numbers: Alphanumeric codes like "P300123456" are unreliable in general STT

The OpenAI Realtime API solves this by processing raw audio directly with function calling, extracting structured data without an intermediate text representation.

AUTH_MODE Toggle

The AUTH_MODE environment variable controls which path is used (settings.auth_mode):

  • standard (default): Deepgram STT + LangGraph auth node for all phases. PII is parsed from text transcripts using validators in utils/pii_validator.py.
  • realtime: OpenAI Realtime API handles the entire auth conversation (STT + NLU + TTS + barge-in). Once auth completes, the system switches to Deepgram + LangGraph for post-auth intents.

How The Switch Happens Mid-Call

In webhooks/twilio_stream.py, the CallHandler class manages the switch:

  1. On _on_start(), if AUTH_MODE=realtime: a RealtimeAuthSession is created and self._auth_active = True
  2. All _on_media() audio is routed to self._realtime_auth.send_audio() instead of Deepgram
  3. The Realtime API handles greeting, PII collection, and TTS natively
  4. When auth completes, _on_realtime_auth_done() fires:
    • Sets self._auth_active = False
    • Closes the Realtime WebSocket
    • Persists auth result to Redis session
    • Acquires the access token for downstream API calls
    • Creates a new STTService (Deepgram) for post-auth conversation
  5. From this point, all audio flows through Deepgram + LangGraph

Function Calling for Structured PII Extraction

The Realtime API session is configured with five function tools:

FunctionParametersTrigger
collect_phonedigits: string (10 digits only)Caller provides phone number

Each function call returns an instruction string that tells the model what to say next (e.g., "Phone matched. Ask for the insured's date of birth."). The model never sees PII data from the backend — it only receives instructions about what to ask next.

Key Architectural Decision: Auth as Guard, Not Node

Authentication is not a separate node in the graph. Instead, each restricted service node calls ensure_authenticated(state, node_name) at its entry point. This design has two benefits:

  • Active flow preservation — while auth is in progress, active_flow is set to the requesting service node (e.g., "policy"). This means the router routes all PII utterances back to that same service node, which re-enters the auth guard, which advances the auth state machine. When auth completes, the service node executes immediately on the same turn.
  • No dead-end state — a separate auth node would require the user to re-state their intent after authentication. With the guard pattern, the original intent is preserved.

Checkpointing

LangGraph's checkpointer saves state after each node transition. The system initializes PostgreSQL checkpoint tables via PostgresSaver.setup() at startup, then uses MemorySaver for the actual graph execution (the async-compatible checkpointer). The thread_id is the Twilio call_sid, enabling:

  • Crash recovery — if the server restarts mid-call, the checkpoint table preserves the last graph state
  • Multi-turn continuity — each ainvoke() loads the last checkpoint for that thread_id
  • Graceful fallback — if PostgreSQL is unreachable, falls back to in-memory checkpointing with a logged warning

5 Intent Router

LLM-Based Intent Classification

The router does not use keyword matching for primary intent detection (though it does use keyword pre-checks for escalation, goodbye, and privacy to save LLM calls). The core classification sends the caller's utterance to the LLM with a tightly constrained prompt:

System: "You are a call intent classifier. Reply with ONE word only."
Human:  ROUTER_PROMPT.format(utterance=last_human)
LLM config: temperature=0, max_tokens=20

The prompt lists all 12 valid intents with descriptions and examples. The response is lowercased, underscored, and validated against VALID_INTENTS. Unrecognized outputs default to "faq".

Dual Model Strategy

UseLLMConfigWhy
Intent Routerget_router_llm()temp=0, max_tokens=20Fast, deterministic single-word output; ~100ms response time
Service Nodesget_llm()temp=0.3, max_tokens=200Natural conversational responses; slightly creative but controlled

Both can run on either Groq (Qwen 27B, default) or Bedrock (Nova Micro), toggled by LLM_PROVIDER env var. This dual-provider design means the system can run entirely on AWS (Bedrock) without any external API dependencies, or use Groq for faster/cheaper inference during development.

Context Switch Enforcement

When a caller is inside a multi-step flow (e.g., payment), the router enforces context switch rules before LLM classification to prevent accidental pivots:

ModeBehaviorFlows
lockedNo intent change allowed (except escalation). LLM not even called.OTP (DTMF payment entry)
escalate_onlyLLM classifies, but non-escalation intents are suppressed → stay in flow.policy, payment, loan, beneficiary, contact, document, privacy
openFull LLM classification; caller can freely pivot.faq, escalation

Pre-LLM Keyword Checks (Ordered)

  1. Goodbye keywords — bypass auth wall (callers who dialed by mistake must be able to leave)
  2. Caller-name collection step — all input goes to auth node (prevents names like "Agent" from triggering escalation)
  3. Privacy phrases — pre-check before escalation (LLM tends to misclassify "how do you use my data" as escalation)
  4. Escalation keywords — always honoured regardless of flow lock
  5. Auth in progress — route back to active service node without LLM call
  6. Confirmation negation — "no, that is wrong" in escalate_only flows stays in flow (prevents LLM misclassification)

Retry Logic

LLM invocation uses exponential backoff retry for transient errors (Groq 503/429, Bedrock throttling): 3 attempts with delays of 1s and 2s. If all retries fail, the router falls back to the active flow's intent or escalation.

2-PII Match Requirement

Authentication requires matching exactly 2 pieces of PII against the backend party record. Valid combinations:

Factor 1Factor 2Match Method
Phone numberDate of birthExact match
Phone numberInsured nameFuzzy match (SequenceMatcher ≥ 0.80)
Policy numberDate of birthExact match
Policy numberInsured nameFuzzy match (SequenceMatcher ≥ 0.80)

Name matching uses difflib.SequenceMatcher with a 0.80 threshold on both first and last name independently, allowing for minor STT transcription errors.

ANI Check

While the architecture supports ANI (Automatic Number Identification) — the caller's phone number is captured in the webhook's From field and stored in session — the current implementation always starts by asking for the phone number rather than auto-matching ANI. This is a deliberate choice: many callers call from numbers not on their policy (spouse's phone, work phone, etc.).

Retry Logic and Escalation

  • max_auth_attempts = 3 (configurable via env var)
  • Per-slot retry: each PII field tracks blank (no input), invalid (wrong format), and asked (initial prompt) counts
  • 2 blank responses on any single slot → escalate to agent
  • If caller says "I don't know" to phone → skip to policy number. IDK to DOB → skip to name. IDK to name or policy → escalate.
  • If both DOB and name verification fail after successful party search → escalate

Post-Auth: Caller Persona Identification

After 2-PII match succeeds, the system asks "May I ask your name please?" and matches the response against the policy's persona list (from finalized_party["Personas"]). This determines access level:

  • payor / insured / owner → full access to policy data and service flows
  • other → restricted: cannot access policy, payment, loan, beneficiary, etc. Offered transfer to a representative.

Persona matching uses partial word matching: "John" matches "John Smith". Conversational prefixes ("My name is", "It's", "I am") are stripped before matching.

Why Split Across Two Stores

The split is a deliberate durability vs. speed trade-off:

  • Redis: Call sessions are inherently ephemeral — a call lasts minutes, not days. Redis provides sub-millisecond reads/writes with automatic TTL cleanup. No schema needed; state is JSON-serialized.
  • PostgreSQL: Call history must survive server restarts for the dashboard. LangGraph checkpoint tables require SQL. pgvector needs PostgreSQL. One database handles all three concerns.

Every fallback logs a warning but never crashes the IVR. The design philosophy is: a call must never fail because a backing store is down.

Redis Session Schema

Key pattern: cno:session:{call_sid}. Value: JSON-serialized CNOState dict. Messages are serialized via LangChain's model_dump(). TTL is refreshed on every save_state() call (1-hour sliding window).

PostgreSQL Call Records

Table: ivr_call_records(call_sid TEXT PK, data JSONB, started_at TIMESTAMPTZ, updated_at TIMESTAMPTZ). The full call dict (turns, events, metadata) is stored as JSONB, so no schema migration is needed when new fields are added. Write-through: every add_call_turn() and update_call_metadata() call writes to both in-memory cache and PostgreSQL. On startup, init_from_db() loads the last 100 records to populate the dashboard.

    v
Grounded voice response → TTS → caller

Knowledge Base

The knowledge base is populated by seed_knowledge.py, which contains ~50+ insurance FAQ chunks covering:

  • Policy types (whole life, term life, universal life)
  • Premium payments and billing
  • Loan provisions and interest
  • Beneficiary rules and changes
  • Document delivery policies
  • Privacy / GLBA opt-out
  • Claims and surrender procedures

Each chunk includes metadata: category, subcategory, and keywords for filtering (though currently similarity search doesn't filter by metadata).

Why pgvector Over Pinecone/Weaviate

  • Operational simplicity — no additional service to deploy/manage; piggybacks on the existing PostgreSQL instance
  • Scale — the FAQ knowledge base is small (~50-100 documents); pgvector handles this trivially
  • Cost — zero additional cost; included in the RDS instance already provisioned
  • Latency — same-VPC query to PostgreSQL is sub-10ms for small collections

Authentication for API Calls

All API calls use two layers of auth:

  1. System API key (CNO_API_KEY) — Authorization: Bearer header on party_search and auth_token
  2. Session access token — acquired via /auth/token after 2-PII match; used as Bearer token on all subsequent policy/payment/loan calls

Sidecar Deployment

The mock API runs as a second container in the same ECS task definition (Dockerfile.mock). It exposes port 8001 and is accessible from the app container at http://localhost:8001 because ECS Fargate containers in the same task share a network namespace. The mock API is a FastAPI app (mock_cno_api.py) that returns realistic test data.

10 Telephony Layer (Twilio)

Twilio Media Streams

The primary voice path uses Twilio Media Streams for bidirectional WebSocket audio. When a call arrives:

  1. POST /webhook/voice returns TwiML that starts a <Stream> to wss://server/stream
  2. Twilio opens a WebSocket connection and begins streaming mulaw audio events
  3. Events: connected, start (with callSid, streamSid, customParameters), media (audio payload), dtmf (keypad digit), stop
  4. The server sends media events back to play TTS audio, and clear events to flush buffered audio on barge-in

Webhook Path (Alternative)

A REST-based webhook path also exists via /webhook/voice + /webhook/gather using Twilio's <Gather> for STT and <Say> with Polly.Joanna for TTS. This is simpler but higher-latency and doesn't support barge-in or streaming TTS. It uses the LangGraph checkpointer for multi-turn state (only messages and call_sid are sent per invocation; all other state is preserved in the checkpoint).

Browser Softphone

The /client endpoint serves a browser-based softphone using the Twilio Voice JS SDK:

  1. GET /client/token generates a Twilio Access Token with a VoiceGrant tied to the TwiML App SID
  2. The TwiML App's Voice URL points to /webhook/voice
  3. Browser calls device.connect() → Twilio initiates a call → hits the voice webhook → starts Media Stream

DTMF Handling

DTMF digits arrive as separate events on the WebSocket alongside audio. The DTMFCollector class accumulates digits for payment collection:

  • Card flow: card_number (16 digits, terminated by #) → expiry (4 digits MMYY #) → CVV (3-4 digits #) → amount (# to submit)
  • Bank flow: routing_number (9 digits #) → account_number (#) → amount (#)
  • * acts as backspace within a field
  • During DTMF collection, _dtmf_mode = True suppresses STT transcript processing

Call Transfer

When a service node sets transfer_to (escalation), the WebSocket handler calls the Twilio REST API to update the call with redirect TwiML: <Response><Dial>{phone}</Dial></Response>.

11 Text-to-Speech

OpenAI TTS Streaming

The current TTS implementation uses OpenAI's streaming TTS API (tts-1 model, nova voice) via the TTSService class. The settings also support ElevenLabs (keys are configured) but the active implementation streams from OpenAI.

Audio Pipeline

tts_text (from graph)
    |
    v  normalize_tts_text() — clean for voice output
    |
    v  OpenAI audio.speech.with_streaming_response.create()
    |  model="tts-1", voice="nova", response_format="pcm"
    |  → raw PCM16 24kHz stream
    |
    v  chunk_size=4096 bytes per iteration
    |
    v  audioop.ratecv(chunk, 2, 1, 24000, 8000, state)
    |  Resample 24kHz → 8kHz (factor 1/3)
    |  State maintained across chunks for seamless audio
    |
    v  audioop.lin2ulaw(resampled, 2)
    |  Convert 16-bit PCM → G.711 mulaw
    |
    v  base64-encode → Twilio media event → caller hears audio

Settings include ElevenLabs configuration (API key, voice ID "Rachel", stability/similarity parameters, latency optimization level 3). ElevenLabs offers superior voice quality and more natural prosody, but the current implementation uses OpenAI for simplicity and reduced external dependencies. Three Scaling Policies

MetricTargetScale-Out CooldownScale-In CooldownRationale
CPU Utilization60%60s120sLLM calls and TTS streaming are CPU-intensive; scale before saturation
Memory Utilization70%60s120sWebSocket connections and in-memory session state consume memory proportional to concurrent calls
ALB Requests Per Target1060s120sEach active call maintains a persistent WebSocket; 10 concurrent calls per task is a conservative limit

Cooldown Design

Scale-out cooldown (60s) is shorter than scale-in cooldown (120s) intentionally: the system should add capacity quickly during traffic spikes but be cautious about removing capacity to avoid oscillation. A call may last 3-5 minutes, so premature scale-in would disconnect active callers (though ECS drains connections before stopping tasks).

Capacity Planning for 3,000 Calls/Day

  • 3,000 calls/day = ~375/hour during 8 peak hours
  • Average call duration: ~4 minutes = ~25 concurrent calls at peak
  • At 10 calls/task (ALB scaling target): need ~3 tasks at peak
  • With headroom: max_tasks=8 handles 2x the expected peak
  • Each task at 1 vCPU / 2GB handles ~10 concurrent WebSocket connections comfortably

Key Design Decisions

  • ECR outside Terraform — the ECR repository is created manually (or in a separate bootstrap) so terraform destroy doesn't delete all stored Docker images
  • S3 + DynamoDB state backend — Terraform state is stored in s3://ivr-terraform-state-{account_id}/ivr/terraform.tfstate with DynamoDB locking (ivr-terraform-locks table) to prevent concurrent modifications
  • Image tagging — images are tagged with sha-{short_commit_hash} for traceability, and also as latest for convenience
  • Health check on deploy — after ecs update-service, the pipeline polls /health every 5 seconds for up to 60s (dev) or 90s (prod), failing the deploy if the service doesn't become healthy
  • Prod requires approval — the production GitHub environment has required reviewers, preventing accidental production deploys

15 Security

Security Layers

Twilio Webhook Signature Validation

When VALIDATE_TWILIO_SIGNATURE=true and TWILIO_BASE_URL is set, every inbound Twilio webhook (/webhook/voice, /webhook/gather, /webhook/status, /webhook/recording-status) validates the X-Twilio-Signature header using Twilio's RequestValidator. This HMAC-SHA1 check ensures webhooks genuinely originated from Twilio and prevents spoofed requests. Disabled in dev (no fixed URL).

WebSocket Authentication

The /stream WebSocket endpoint supports token-based auth via query parameter: ?token={WS_AUTH_TOKEN}. When configured, the token is compared using secrets.compare_digest() (constant-time comparison to prevent timing attacks). Unauthenticated connections receive a 4001 close code.

Dashboard HTTP Basic Auth

The /dashboard/* and /client/* routes are protected by HTTP Basic Auth when DASHBOARD_PASSWORD is set. Credentials are compared using secrets.compare_digest(). Auth is disabled when the password is empty (dev mode).

AWS Secrets Manager

All API keys (OpenAI, Deepgram, ElevenLabs, Twilio, Groq) are stored in Secrets Manager at {env}/ivr/app-secrets. ECS task definitions reference them as secrets (not environment variables), so they're injected at container start without appearing in task definition plaintext or CloudWatch logs.

PII Protection

  • PII redaction: utils/pii_redactor.py strips sensitive data from conversation logs stored in the dashboard
  • Card/bank data collected via DTMF only — never passes through the LLM or STT pipeline
  • Payment API calls use JWT (X-Payment-JWT) with 5-minute expiry for authorization
  • System prompt explicitly prohibits the LLM from revealing or hinting at data from internal records

Live Log Streaming via SSE

The log_bus.py module implements an in-memory pub/sub system:

  1. main.py's _Tee class intercepts all stdout/stderr and calls log_bus.push(line)
  2. log_bus maintains a ring buffer (deque(maxlen=500)) and a list of subscriber queues
  3. GET /client/logs/stream returns a Server-Sent Events stream that subscribes to log_bus
  4. The log viewer page (GET /client/logs) connects to this SSE endpoint and color-codes log lines by type (speech=blue, auth=orange, graph=green, error=red)

Dashboard

The /dashboard endpoint serves a comprehensive monitoring UI with tabs for:

  • WebChat — text-based testing interface
  • Calls — call history with turn-by-turn transcripts, intents, nodes, and timing
  • Softphone — browser-based voice testing
  • Logs — real-time log stream with filtering
  • Config — current system configuration (models, providers, feature flags) with masked API keys

Call Recording

The webhook path (/webhook/voice) starts a Twilio recording on each call. When the recording completes, Twilio fires /webhook/recording-status, which stores the recording SID and MP3 URL in the conversation store for later review.
