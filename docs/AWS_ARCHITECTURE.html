6. RAG Pipeline on AWS

End-to-end flow

1. Caller Query
Natural language from Deepgram STT → ECS Fargate IVR App
2. Redis Cache Check (ElastiCache)
SHA256(query) lookup — hit returns in 2-5ms, skip steps 3-6
3. Category Detection
Keyword matching <1ms → narrows pgvector search to relevant category
4. Embed Query (OpenAI API or SageMaker)
text-embedding-3-small via HTTPS ~80ms — future: SageMaker VPC endpoint ~30ms
5. Vector Search (RDS pgvector)
HNSW ANN search with metadata filter via run_in_executor — 9 candidates ~50-100ms
6. LLM Re-Rank (Groq API)
qwen/qwen3.8-27b scores 9 candidates in parallel → top 3 ~200ms
7. Cache & Return
Store in ElastiCache (1hr TTL), return concatenated context to FAQ node
8. LLM Answer (Groq qwen/qwen3.8-27b)
Grounded 1-2 sentence voice answer → ElevenLabs TTS → Twilio → caller

Cache Hit Latency

2-5 ms

Cache Miss Latency

350-500 ms

(embed 80 + search 100 + rerank 200 + overhead 50)

10. Guardrails & Content Safety

Insurance IVR handles sensitive financial data (policy numbers, SSN, bank accounts). Guardrails prevent hallucination, PII leakage, prompt injection, and off-topic responses.

Guardrail layers

Input Guardrails (before LLM) — PII detection & redaction in logs, prompt injection detection, topic boundary enforcement
RAG Guardrails (retrieval) — Context grounding (answer ONLY from retrieved chunks), source attribution, confidence threshold (skip if similarity < 0.5)
Output Guardrails (after LLM) — Financial advice prohibition, PII masking in TTS, response length limits (max 2 sentences), hallucination detection
Compliance Guardrails (regulatory) — GLBA privacy script enforcement, ACH authorization script, call recording disclosure, relationship restriction
AWS Bedrock Guardrails (optional) — Denied topics (investment/legal/medical advice), PII filters (SSN, cards), content filters, grounding check. ~$1/1000 text units.

Implementation mapping

GuardrailImplementationAWS Service
PII redactionutils/pii_redactor.py (regex)Comprehend (optional)
Prompt injectionSystem prompt hardening + keyword detectionBedrock Guardrails (optional)
Topic enforcementRouter node intent classificationBuilt-in (LangGraph)
Context groundingFAQ prompt: "Use ONLY the following context"Built-in (RAG pipeline)
Financial advice blockSystem prompt prohibitionBuilt-in
Response lengthmax_tokens=200Built-in (LangChain)
PII in logspii_redactor strips SSN/cards from logsCloudWatch log filtering
Compliance scriptsRAG knowledge base includes exact scriptsBuilt-in (seed_knowledge.py)

13. Document Ingestion Pipeline

Architecture

S3 (upload) --> Lambda (trigger + validate) --> SQS (queue) --> ECS Task (worker) --> RDS pgvector
                                                                      |
                                                                OpenAI API (embedding)

Flow

  1. Upload: PDF/text/CSV uploaded to s3://uic-ivr-knowledge/incoming/
  2. Trigger: S3 event fires Lambda function
  3. Validate: Lambda checks file type, size (<50MB), optional virus scan
  4. Queue: Lambda puts message on SQS with S3 key + metadata
  5. Process: ECS worker picks up SQS message
  6. Load: Download from S3, run appropriate loader (PyPDF, TextLoader, CSVLoader)
  7. Chunk: RecursiveCharacterTextSplitter (500 chars, 50 overlap)
  8. Enrich: Auto-detect category, add metadata
  9. Embed: Call OpenAI API for embeddings
  10. Store: Insert into pgvector
  11. Invalidate: Clear Redis RAG cache
  12. Notify: SNS on success/failure
Why SQS between Lambda and ECS? Decoupling (Lambda returns immediately), retry (3 attempts then DLQ), rate limiting (won't overwhelm OpenAI API), visibility (queue depth metrics).

15. Security Architecture

Defense in depth

Network: VPC isolation (private subnets for DB/cache), security groups (least privilege), WAF on ALB (DDoS, injection), NACLs
Identity & Access: IAM roles for ECS tasks (least privilege), RDS IAM auth, Secrets Manager for API keys, no long-lived credentials
Data Protection: RDS encryption at rest (AES-256 KMS) + in transit (TLS 1.2+), ElastiCache encryption, S3 SSE, PII redaction in logs
Application: Twilio webhook signature validation, WebSocket auth token, dashboard HTTP Basic auth, CORS restriction, input validation
Compliance: GLBA privacy controls, PCI DSS considerations, SOC 2 audit trail (CloudTrail), HIPAA-eligible services

16. CI/CD Pipeline

Current setup: CI/CD uses GitHub Actions (.github/workflows/deploy.yml) pushing to ECR + ECS force-deploy, not CodePipeline. The CodePipeline stages below represent the target production pipeline.
Stage 1: Source
GitHub main branch → CodePipeline via CodeStar connection
Stage 2: Build (CodeBuild)
docker build → push to ECR → pytest → ruff lint
Stage 3: Test (CodeBuild)
eval_intents.py, eval_rag.py, eval_slots.py — fail if faithfulness < 0.80
Stage 4: Deploy Staging
Update ECS service (staging cluster) → smoke tests
Stage 5: Manual Approval
SNS notification → reviewer approves in console
Stage 6: Deploy Production
Blue/green via CodeDeploy → health check → auto-rollback on failure

Blue/green deployment

               ALB
              /    \
+------------+      +-------------+
| Blue (v1)  |      | Green (v2)  |
| (current)  |      | (new)       |
+------------+      +-------------+

1. Deploy v2 to green target group
2. ALB health checks pass on green
3. Switch ALB traffic: blue -> green
4. Monitor 5 minutes
5. If errors: auto-rollback to blue
6. If stable: drain and terminate blue

20. Migration Plan (Dev to Prod)

Phase 1: Infrastructure Setup (Week 1)

  • Create VPC with public/private subnets across 2 AZs
  • Set up security groups
  • Deploy RDS PostgreSQL with pgvector extension
  • Deploy ElastiCache Redis
  • Set up NAT Gateway
  • Create ECR repository
  • Store all API keys in Secrets Manager
  • Set up CloudWatch log groups

Phase 2: Application Deployment (Week 2)

  • Build Docker image, push to ECR
  • Create ECS cluster, task definition, service
  • Configure ALB with WebSocket support
  • Set up TLS certificate (ACM)
  • Configure WAF rules
  • Deploy to staging, run smoke tests

Phase 3: Data Migration (Week 2-3)

  • Create S3 bucket for knowledge documents
  • Upload knowledge base documents
  • Run document ingestion pipeline
  • Verify pgvector data integrity
  • Create HNSW index if vectors > 500
  • Run RAG evaluation suite

Phase 4: Testing & Validation (Week 3)

  • Full evaluation suite (intents, RAG, slots, e2e)
  • Load test: 50 concurrent calls
  • Failover test: kill primary RDS, verify auto-failover
  • Cache test: verify Redis failover
  • Security scan: WAF, SGs, IAM policies

Phase 5: Go-Live (Week 4)

  • Set up CI/CD pipeline (CodePipeline)
  • Configure CloudWatch alarms and dashboards
  • Set up on-call rotation (PagerDuty/SNS)
  • DNS cutover (Route 53)
  • Monitor first 24 hours
  • Document runbook for operations team
