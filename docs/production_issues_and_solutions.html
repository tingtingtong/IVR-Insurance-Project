01
15-20s Silence During Policy/Payment Lookups
Latency UX
▶
Problem

Each service node (policy, payment, loan, beneficiary) makes sequential calls: first a backend API call (up to 10s timeout), then an LLM call to format the response (2-5s). The caller hears nothing during this entire window.

Files
core/graph/nodes/policy.py:42-67 payment.py:41-68 loan.py:29-47
Impact
  • Callers perceive a dead line after ~5s of silence
  • Industry data: 60% of callers hang up after 10s of silence
  • 15-20s gap causes most callers to abandon or repeat, creating duplicate processing
Solution
  • Add intermediate filler TTS: "Let me look that up for you..." before the API call
  • Stream LLM response token-by-token into TTS (overlap generation + synthesis)
  • Set aggressive API timeouts (5s) with cached fallback for recently queried policies
02
Auth Flow Creates 30s+ Cumulative Latency
Latency UX
▶
Problem

Every phone/policy lookup triggers a fresh party_search API call with 10s timeout. A typical 2-retry auth flow: 3 API calls x 10s = 30s of waiting. No intermediate prompt means callers hear silence and repeat themselves.

Files
core/graph/nodes/auth.py:178-264 core/tools/party_search.py:32-44
Solution
  • Cache party_search results for the session (phone number rarely changes mid-call)
  • Add "One moment while I verify..." filler TTS before each API call
  • Pre-fetch party data during phone number confirmation step
03
No Connection Pooling Exhausts File Descriptors Under Load
Scalability Reliability
▶
Problem

Every backend API call creates and destroys a new aiohttp.ClientSession(). Each session opens a new TCP connection (~50-100ms overhead per call). At 100 concurrent calls x 3 API calls = 300 simultaneous TCP connections, hitting Linux file descriptor limits (1024).

Files
core/tools/party_search.py auth_token.py payment_api.py holding_inquiry.py contact.py document.py
OSError: Too many open files - server crashes entirely. All in-flight calls dropped.
Solution
  • Create a shared aiohttp.ClientSession at startup with TCPConnector(limit=100)
  • Inject via FastAPI dependency or module-level singleton
  • Add connection keep-alive to reuse TCP connections
04
MemorySaver Loses All In-Flight Calls on Restart
Reliability Scalability
▶
Problem

main.py:92 uses MemorySaver() as the LangGraph checkpointer even when PostgreSQL is available. All graph state lives in-process memory. A server restart (deploy, crash, OOM kill) instantly loses state for every active call.

Files
main.py:59-96
Solution
  • Use AsyncPostgresSaver for the graph checkpointer (not just table setup)
  • Implement graceful shutdown that drains active calls before restart
  • Add health check warning when >N calls are in-flight before deploys

06
Groq 503/429 Errors Cause Unnecessary Agent Transfers
Reliability UX
▶
Problem

Backend API calls in tool functions have no retry logic. A single transient 503 or network blip returns failure and escalates to a live agent. The router node has retry logic, but service nodes and tools do not.

Files
core/tools/party_search.py:32-44 core/tools/auth_token.py:33-52
Groq returns 503s under load at ~1-3% rate. Without retry, these become false escalations - real callers queued behind fake transfers.
Solution
  • Add exponential backoff retry (1s, 2s) for 503/429 in all tool functions
  • Distinguish retryable errors (503, 429, timeout) from permanent (400, 404)
  • Log retry attempts for monitoring dashboards
07
DTMF Race Condition Can Cause Duplicate Payment Processing
PCI Reliability
▶
Problem

DTMF completion fetches state from Redis, merges OTP data, and invokes the graph. If two DTMF events arrive close together, both read stale state and both invoke the graph - potentially processing a payment twice.

Files
webhooks/twilio_stream.py:336-346
PCI compliance violation + direct financial risk. Duplicate charges require manual refunds and erode customer trust.
Solution
  • Add Redis-based distributed lock (SETNX) before DTMF processing
  • Use optimistic locking with state version numbers
  • Debounce DTMF events with 500ms window before processing
08
Deepgram Connection Drop Makes Caller "Deaf"
Reliability UX
▶
Problem

If the Deepgram WebSocket drops mid-call, the STT handler silently catches the exception. No reconnection, no fallback to webhook STT. The caller keeps speaking but the bot hears nothing. Repeated timeouts until Twilio disconnects at 60s.

Files
services/stt.py:76-90
Solution
  • Implement Deepgram WebSocket auto-reconnect with exponential backoff
  • Add "no transcript received" watchdog (15s = reconnect)
  • Fall back to Twilio <Gather> webhook STT if reconnect fails

Silent Transfer Failures Leave Callers Stranded
UX Reliability
▶
Problem

If the Twilio API returns an error during agent transfer (invalid phone, account limits), the exception is logged but the caller receives no TTS notification. They hear "Please hold..." followed by silence, then disconnection.

Files
webhooks/twilio_stream.py:469-484
Solution

  • Log transfer failures as critical alerts for ops monitoring

Compliance Scalability

Files

The 800ms Latency Ceiling
Latency
▶
Problem

2026 industry benchmark: acceptable voice AI response time is under 800ms end-to-end. Typical pipeline: STT (100-300ms) + LLM (350-1,000ms) + TTS (90-200ms) + network (50-200ms). LLM inference alone = 70% of total latency.

A five-service pipeline across providers adds 500-1,000ms in pure network transit before any AI processing begins.
Industry Solution
  • Streaming pipeline overlap: STT sends partials while caller talks; LLM starts before full input; TTS synthesizes from first tokens. Cuts 300-600ms/turn
  • Speech-to-speech models skip STT-LLM-TTS relay, saving ~600ms
  • Co-locate all services in the same cloud region

Latency
▶
Data Points

Production testing of gpt-realtime-2 over 40 calls: p50 = 1.1s, p95 = 1.9s. Optimized implementations reduced p95 to 320ms (50% reduction) by using streaming APIs and eliminating the STT-LLM-TTS relay.

Industry Solution
  • Use WebRTC over WebSockets (UDP vs TCP = lower latency)
  • Speculative LLM generation during VAD silence detection
  • Pre-warm LLM connections to eliminate cold-start per turn

Authentication Failure Loops Lock Out Legitimate Callers
UX Reliability
▶
Problem

Knowledge-based auth (DOB, SSN, policy number) causes legitimate customers to fail 10-30% of the time. Reasons: wrong DOB format, middle vs first name, married vs maiden name. Overly aggressive auth inflates escalation rates by 15-25%.

Industry Solution
  • Use ANI (caller phone number) as first-factor match before questions
  • Voice biometrics as passive second factor
  • Fuzzy name matching (Soundex/phonetic similarity > 80%)
  • Limit to 2 PII factors (not 3+) for phone-based auth
15
Barge-In False Triggers Derail Conversations
UX Reliability
▶
Problem

Agent cuts itself off when user wasn't interrupting. Three patterns: (1) background noise triggers VAD, (2) side conversations trigger VAD, (3) echo from agent's own audio feeds back.

Production targets: barge-in latency <400ms, false barge-in <2%, missed true interruptions <1%.
Industry Solution
  • Smart Turn Detection models (e.g., Pipecat Smart Turn v3)
  • 5-scenario barge-in test matrix: true correction, backchannel, noise, DTMF, timeout
  • Acoustic echo cancellation before VAD processing
  • 300ms debounce window before confirming barge-in intent
16
WebSocket Connection Scaling is Non-Linear
Scalability
▶
Problem

Each voice session holds: WebSocket + STT stream + LLM context + TTS stream. Performance degrades non-linearly. A single stuck WebSocket can back up 50 calls. Single Python process: 20-50 concurrent calls before latency degrades.

Industry Solution
  • 1-container-per-session architecture eliminates concurrency bugs
  • Horizontal pod autoscaling with session affinity
  • WebSocket health checks with automatic reconnection
  • Kill idle connections after 5 minutes

Reliability
▶
Problem

Reported production issue (LiveKit #3379): Twilio WebSocket connects successfully but no media packets are ever received. Mark packets sent from server are never acknowledged. Connection appears healthy but is completely non-functional - a silent failure mode.

Industry Solution

  • Periodic Twilio mark events with acknowledgment verification
  • Alert when media frames = 0 after 5s of connection

An appliance manufacturer's AI generated a "munged-together version of multiple instruction sets" delivering dangerous, incorrect repair instructions. Analysis of 7,246 AI incidents found 188 cases of direct production harm with no attacker involved.

Gartner predicts by 2027, 40% of enterprises will demote or decommission autonomous AI agents due to governance gaps identified only after production incidents.
Industry Solution

  • Output guardrails that validate LLM responses against known data
  • Confidence scoring - escalate to agent when confidence <70%
  • Log every LLM response for post-hoc audit

Cloud STT Regional Latency Spikes
Latency
▶
Problem

Production voicebot on Azure Speech Services (India): 150-250ms TTFB from regional distance. Human conversation gaps = 100-300ms. Voice AI exceeding 500ms feels laggy. Cross-region calls add 50-200ms per hop.

Industry Solution

  • Edge-deployed STT (Deepgram on-prem, Whisper local)
  • Regional failover with latency-based DNS routing
  • Cache frequently used TTS segments (greetings, confirmations)
20
Memory Leaks in Long-Running Voice Pipelines
Scalability Reliability
▶
Problem

Unconsumed frames queue in memory indefinitely. Abandoned sessions (caller hangs up, WebSocket lingers) leak continuously. Pipecat's SmallWebRTCTransport had a confirmed leak. Memory grows ~500KB/session/minute for orphaned connections.

Industry Solution
  • Session TTL with automatic cleanup (max 30 min call duration)
  • Kill connections exceeding 50MB
  • Explicit cleanup handlers for WebSocket on_close
  • Docker --memory flag as safety net
  • Periodic GC sweeps for orphaned session state
