1 System Design & LangGraph

1 Why did you choose LangGraph as the orchestration layer instead of a traditional IVR platform like Avaya Experience Portal or Dialogflow CX?Foundational ▼

Key points to cover:

  • Full control over graph structure — LangGraph gives us a directed stateful graph where every node, edge, and conditional transition is explicit Python code. Traditional IVR platforms use proprietary visual builders that hide routing logic and limit customization.
  • First-class state management — CNOState is a TypedDict with 20+ fields (auth state, PII collected, current intent, slot attempts, etc.). LangGraph's state reducers (like add_messages) handle conversation history natively. Traditional IVRs use session variables with limited nesting.
  • LLM-native — Every node can call different LLMs (Groq for routing, OpenAI Realtime for PII collection) without adapter layers. DFCX requires you to stay within Google's ecosystem.
  • Composability — Nodes are async Python functions. We can call external APIs (party search, holding inquiry), run fuzzy matching, and do multi-step auth logic inside a single node without framework constraints.
  • PostgreSQL checkpointing — Built-in checkpoint support persists conversation state. On crash or reconnection, the graph resumes from the last checkpoint without re-running prior nodes.

Tradeoff acknowledged: Steeper learning curve than visual IVR builders; requires explicit error handling (no built-in retry/fallback patterns); debugging requires understanding graph traversal rather than looking at a visual flow.

2 Describe the graph topology. How many nodes do you have, how are edges defined, and how does the router dispatch to service nodes?Intermediate ▼

Topology:

START → router → [conditional edges] → {policy, payment, otp, loan, beneficiary,
                                         contact, document, privacy, faq,
                                         escalation, goodbye, auth} → END
  • Single entry point: Every user turn enters at START → router.
  • Router node: Calls the fast-tier LLM (Groq) with a minimal prompt to classify intent into one of 12 categories. Output is a string like "policy_info" or "payment,loan" (multi-intent).
  • Conditional edges: add_conditional_edges("router", route_intent) — a Python function reads state["current_intent"] and returns the target node name.
  • All service nodes → END: Flat topology — no cycles or loops in the graph. Each turn produces one response. Multi-turn conversations are achieved via checkpointing (the graph re-enters at START each turn with full prior state).
  • Multi-intent queuing: If the router returns "policy_info,payment", the first intent is dispatched immediately, and "payment" is pushed to state["pending_intents"]. After the first flow completes, the router dequeues the next intent.
3 Walk me through the CNOState TypedDict. What are the key state fields, and why is separating conversation, auth, and flow-control state important?Intermediate ▼

Three logical layers in CNOState:

1. Conversation layer:

  • messages — Full LangChain message history with add_messages reducer (appends, never overwrites)
  • call_sid, stream_sid — Twilio call identifiers for correlating logs and managing WebSocket streams

2. Authentication layer:

  • authenticated (bool), auth_step (string like "collecting_phone", "verifying_dob"), auth_attempts (int)
  • pii_collected (dict) — What the caller has given us so far: phone, policy, DOB, name
  • candidate_party — The API record we're matching against
  • customer — Final verified identity (populated only after auth success)
  • caller_persona — "payor", "insured", "owner", "other" — determines data access rights

3. Flow control layer:

  • current_intent, current_node, active_flow — Track which service node owns the conversation
  • pending_intents — Queue for multi-intent utterances
  • slot_attempts — Per-field retry counters (prevents infinite loops on bad input)

Why separate? Auth state must persist across intent changes (caller authenticates for policy, then asks about payment — they shouldn't re-auth). Flow control resets per intent, but auth and conversation layers carry forward. This separation makes each layer independently testable.

4 How does checkpointing work? What happens if the ECS task crashes mid-call — can the conversation resume?Advanced ▼

Checkpoint mechanism:

  • LangGraph's PostgresSaver writes the full CNOState to PostgreSQL after every node execution.
  • The checkpoint key is call_sid (Twilio's unique call identifier), so each call has its own checkpoint chain.
  • On the next turn, the graph loads the latest checkpoint for that call_sid and resumes from START → router with full prior state.

Crash recovery scenario:

  1. ECS task crashes during the payment node (after auth was completed).
  2. Twilio detects WebSocket disconnect and can retry the connection (if configured with <Connect> retry).
  3. New ECS task picks up the call. The graph loads the last checkpoint from PostgreSQL.
  4. State shows authenticated=true, customer={...}, active_flow="payment".
  5. The caller doesn't need to re-authenticate — the conversation continues from where it left off.

Fallback: If PostgreSQL is unreachable, the system falls back to an in-memory checkpointer (no persistence across restarts, but still works within a single task lifecycle).

Tradeoff: Every node transition incurs a DB write (~5-10ms). For a voice IVR where we target sub-second response times, this is acceptable but not free.

5 Explain the context-switch enforcement strategy. What are the "locked", "escalate_only", and "open" modes, and why are they needed?Advanced ▼

Context switching is critical because callers can say anything at any time, and the LLM might try to pivot to a new intent mid-flow. We need guardrails:

CONTEXT_SWITCH_CONFIG = {
    "otp":       "locked",         # PCI DTMF entry — NO interruption
    "payment":   "escalate_only",  # Only agent transfer allowed
    "policy":    "escalate_only",
    "loan":      "escalate_only",
    "faq":       "open",           # Full pivoting allowed
    "escalation":"open",
}

Locked mode (OTP): During card number DTMF collection, the caller's speech is ignored entirely. The router forces the turn back to the OTP node without even calling the LLM. This prevents PCI-sensitive flows from being interrupted.

Escalate-only mode: The router calls the LLM for intent classification, but if the result is anything other than "escalate" or "goodbye", it's suppressed — the turn goes back to the active flow. This allows callers to say "transfer me to an agent" (safety exit) but prevents random topic pivots mid-transaction.

Open mode: Full LLM classification; the caller can pivot to any intent. Used for FAQ and escalation flows where there's no stateful transaction to protect.

Special bypasses (always honored regardless of mode):

  • Goodbye — keyword detection ("bye", "that's all"), never blocked
  • Escalation — keyword detection ("agent", "representative"), always honored as a safety exit

2 LLM Strategy & Voice AI

6 Why a dual-LLM tier architecture? Why not use a single model for everything?Foundational ▼

Two tiers optimized for different concerns:

Tier 1 — Router LLM (Groq, Qwen 27B):

  • Purpose: Single-turn intent classification
  • Config: temperature=0, max_tokens=20
  • Latency: Sub-200ms (Groq's custom LPU hardware)
  • Cost: Minimal (tiny output per call)
  • Why Groq? Traditional cloud LLM APIs (OpenAI, Bedrock) have 400-800ms inference. For voice, every 100ms matters because the caller is waiting in silence. Groq delivers 10x faster inference.

Tier 2 — Service LLM (same Groq model, higher token budget):

  • Purpose: Generate natural voice responses from API data
  • Config: temperature=0.3, max_tokens=200
  • Uses the full system prompt with voice IVR rules (speak naturally, use contractions, etc.)

Why not one model? The router is called on every single turn. If we used a large model (GPT-4, Claude) with the full system prompt for routing, we'd add 500ms+ to every turn just for intent classification. The dual-tier approach lets us use a fast/cheap model for the frequent routing decision and a slightly richer call for response generation.

Provider toggle: LLM_PROVIDER env var switches both tiers between Groq and Amazon Bedrock (Nova Micro). Bedrock is the fallback for production if Groq has availability issues.

7 What happens when the Groq API returns a 503 or 429 mid-call? Describe the failover strategy.Intermediate ▼

Multi-layer failover:

  1. Retry with exponential backoff: On 503/429, the router retries up to 2 times with delays of 1s and 2s. For a voice call, waiting 3s total is the maximum acceptable — beyond that, the caller perceives a "dead line."
  2. Provider fallback: If all retries fail, the system can switch to the Bedrock provider (amazon.nova-micro-v1:0). This is configured at the LLM_PROVIDER level — currently a manual environment variable change, but could be automated with a circuit breaker.
  3. Graceful degradation: If both LLM providers fail, the router falls back to keyword matching (escalation keywords, goodbye keywords) and routes to escalation node with a message like "I'm having trouble right now. Let me connect you with an agent."

What we don't do: We never play silence. If the LLM is slow, we play a filler prompt ("One moment please") before the response arrives, so the caller always hears something.

8 You use both Deepgram and OpenAI Realtime API for speech-to-text. Why two STT engines, and when does each one activate?Intermediate ▼

Dual STT strategy for accuracy vs. latency optimization:

Deepgram (primary, all general conversation):

  • Model: nova-2 (streaming, real-time)
  • Encoding: mulaw 8kHz (native Twilio codec — no transcoding needed)
  • Endpointing: 300ms silence detection to finalize utterances
  • Smart formatting: Auto-formats dates, phone numbers, currency values
  • Strength: Fast (sub-300ms), cost-effective, good general accuracy

OpenAI Realtime API (optional, PII collection only):

  • Activates when auth_mode: "realtime" is configured
  • Raw audio → OpenAI Realtime (STT + LLM + TTS in one pipeline)
  • Eliminates the intermediate STT→text→LLM pipeline, so the model directly "hears" the audio
  • Strength: Better accuracy for PII (phone numbers, dates of birth, names) because the model can use audio context (prosody, spelling pace) to disambiguate
  • Audio resampling required: mulaw 8kHz (Twilio) ↔ PCM16 24kHz (OpenAI)

Why not Realtime for everything? Cost (Realtime API is significantly more expensive per minute), latency on session creation (~500ms setup), and we don't need audio-level understanding for general conversation. Deepgram handles "What's my policy status?" perfectly; Realtime helps when the caller says "My date of birth is February twenty... no, twenty-third, nineteen sixty-five."

9 Describe the TTS pipeline. How do you minimize time-to-first-byte for voice output?Intermediate ▼

Primary TTS: ElevenLabs (streaming WebSocket)

  • Voice: "Rachel" (voice ID: 21m00Tcm4TlvDq8ikWAM)
  • Model: eleven_monolingual_v1
  • Optimize streaming latency: 3 (scale 0-4, where 4 is max speed, lower quality)
  • Stability: 0.5, Similarity boost: 0.75 — balanced for natural-sounding IVR

Latency minimization techniques:

  1. Streaming: ElevenLabs returns audio chunks via WebSocket as soon as the first few words are synthesized — we don't wait for the full response. First audio byte arrives in ~200ms.
  2. Sentence-level streaming: The LLM's response is streamed token-by-token. As soon as a complete sentence is formed, it's sent to TTS. The caller starts hearing the response before the LLM finishes generating.
  3. Codec match: Output is mulaw 8kHz — the same codec Twilio expects. No transcoding delay.
  4. Connection reuse: The ElevenLabs WebSocket stays open for the duration of the call, avoiding per-turn connection overhead.

Fallback TTS: OpenAI TTS (tts-1, voice: nova) — activated if ElevenLabs is unreachable. Uses the lower-quality but faster tts-1 model, not tts-1-hd.

10 Walk me through the end-to-end latency budget of a single voice turn. Where does time go, and how did you optimize each segment?Advanced ▼

Target: < 1.5 seconds from end of caller speech to first audio byte of response.

Caller speaks              →  0ms (start)
Twilio Media Stream relay  →  ~50ms (network, mulaw packets)
Deepgram STT (streaming)   →  ~200-400ms (endpointing + final transcript)
Router LLM (Groq)          →  ~100-200ms (intent classification, 20 tokens)
Service LLM (Groq)         →  ~200-400ms (response generation, 200 tokens)
  ↳ First sentence ready   →  ~100ms into generation (streaming)
ElevenLabs TTS (streaming) →  ~200-300ms (time to first audio chunk)
Twilio relay to caller     →  ~50ms (network)
─────────────────────────────────────────────────
Total (first audio byte)   →  ~800-1400ms

Optimizations applied:

  • Groq over GPT-4/Claude: Saves 400-600ms on LLM inference alone
  • Streaming at every layer: STT streams partials, LLM streams tokens, TTS streams audio — nothing waits for a complete result
  • Router + Service split: Router uses 20-token budget (vs. 200 for service), cutting classification time
  • Persistent connections: WebSocket to Deepgram, ElevenLabs, and Twilio stays open — no per-turn handshake
  • Checkpoint async: PostgreSQL checkpoint write happens in parallel with TTS generation

3 Authentication & Security

11 Authentication is implemented as a guard pattern, not a separate graph node. Why this design decision?Intermediate ▼

The auth guard pattern (ensure_authenticated()):

# Inside policy_node:
async def policy_node(state):
    auth_ok, auth_state = await ensure_authenticated(state, "policy")
    if not auth_ok:
        return auth_state  # Returns auth prompt, sets active_flow="policy"
    # Auth complete — proceed with policy lookup
    ...

Why not a separate auth node in the graph?

  • Intent preservation: If auth were a separate node, the flow would be: router → auth → ???. After auth completes, the system would need to ask "Now what did you want?" or maintain a redirect stack. With the guard pattern, the original intent ("policy") is preserved in active_flow, and the caller seamlessly continues.
  • Multi-turn continuity: When auth needs multiple turns (collect phone → verify DOB), each turn re-enters router → policy_node → ensure_authenticated(). The router knows to redirect PII utterances back to the active flow, so the caller's "January 15th 1965" goes straight to the policy node's auth guard.
  • Shared auth, different triggers: Every restricted node calls the same ensure_authenticated(). If the caller is already authenticated from a prior intent, the guard returns (True, state) immediately — zero overhead. No need for explicit "skip auth" edges in the graph.
  • Clean separation: Auth logic lives in auth_guard.py and nodes/auth.py, not scattered across edge conditions. Service nodes don't know auth details — they just call the guard.
12 Describe the multi-factor PII verification flow. What are the valid 2-factor combinations, and how do you handle verification failures?Intermediate ▼

Valid 2-factor combinations (any one = authenticated):

  • Phone number + Date of birth
  • Phone number + Insured name (fuzzy match)
  • Policy number + Date of birth
  • Policy number + Insured name (fuzzy match)

Collection sequence:

  1. Phone number (10 digits) → Call party_search(phone=digits). If found, proceed to DOB. If not found, pivot to policy number.
  2. Policy number (fallback) → Only asked if phone lookup failed. Call party_search(policy_number=parsed).
  3. Date of birth → normalize_dob(utterance) handles natural language ("January fifteenth nineteen sixty-five"). Match against the candidate party record. If match: auth success.
  4. Insured name (fallback if DOB fails twice) → Fuzzy matching with 80% SequenceMatcher threshold to handle STT errors ("Smith" vs. "Smithe").

Failure handling:

  • Each field gets slot_attempts counter (max 2-3 retries per field)
  • Two consecutive blanks on any field → escalate to agent
  • Both DOB and name fail → escalate to agent
  • Max overall auth attempts (3) exceeded → escalate to agent
  • Policy number not found in system → escalate to agent
13 What is caller persona identification, and why is it a separate step from authentication?Intermediate ▼

Authentication ≠ Authorization. Auth verifies the caller can access the account. Persona identification determines what they can access.

Post-auth sub-step:

  1. Auth completes (2-factor PII verified).
  2. System asks: "May I ask your name please?"
  3. Match caller's answer against the Personas list in the party record (payor, insured, owner, etc.).

Matching strategies (in order):

  1. Exact word match (first name or last name matches a persona name)
  2. Substring / starts-with match (handles STT truncation)
  3. Fuzzy match (SequenceMatcher, 75%+ threshold)

Persona outcomes:

  • "payor" / "insured" / "owner" → Full access to policy data, payments, loans, beneficiary info
  • "other" → Restricted. Cannot access policy details, payments, or sensitive data. Router's persona gate blocks these intents and offers agent transfer. FAQ and goodbye still work.

Why separate? A caller might verify identity using the insured person's info (phone + DOB) but actually be calling on behalf of someone else (e.g., a spouse handling billing). Persona identification catches this — you can prove you know the account details but still not be the policyholder.

14 How do you handle PCI compliance for payment card data in a voice IVR?Advanced ▼

Core principle: Card data NEVER passes through the LLM or is stored in conversation logs.

DTMF-only card collection:

  • When the OTP (one-time payment) node reaches card collection, it switches to DTMF mode.
  • The caller presses digits on their phone keypad (not speaking the number).
  • Twilio collects DTMF digits and sends them as structured data, bypassing STT entirely.
  • Context switch is "locked" — the caller's speech is ignored during DTMF entry to prevent accidental card number capture by STT.

Ephemeral JWT for payment API:

  • Before calling the payment API, a JWT is generated with { policyNumber, amount, iat, exp(5min) }.
  • The JWT is sent as X-Payment-JWT header — the payment API validates it independently.
  • 5-minute expiry ensures the token can't be reused after the call.

ACH authorization (Dodd-Frank):

  • Before processing ACH payments, the system reads a verbatim authorization script (regulatory requirement).
  • Caller must confirm consent ("I authorize...") before the transaction proceeds.

What's NOT stored: Card numbers, CVV, bank account numbers are never written to PostgreSQL checkpoints, Redis, CloudWatch logs, or conversation history. The otp_data state field holding these values is ephemeral (in-memory only during the payment flow).

15 What PII protection measures exist beyond PCI? How do you handle data in logs, LLM prompts, and storage?Intermediate ▼

Defense in depth for PII:

1. Log redaction:

  • pii_redactor.py masks sensitive data patterns (SSN, phone numbers, DOB, card numbers) in all log output.
  • API response logs truncate to first 100 characters and redact known PII fields.

2. LLM prompt guardrails:

  • The system prompt explicitly instructs the LLM: "Never reveal, repeat, or hint at internal customer data in your responses."
  • PII fields in state (phone, DOB, name) are used for API calls and matching but never injected into the LLM's response generation prompt.

3. Twilio signature validation:

  • VALIDATE_TWILIO_SIGNATURE=true verifies the X-Twilio-Signature header on incoming webhooks, preventing spoofed requests.

4. WebSocket authentication:

  • Media Stream WebSocket requires a ?token=WS_AUTH_TOKEN query parameter, preventing unauthorized connections.

5. Network isolation:

  • RDS and Redis are in private VPC subnets — no public endpoints.
  • Security groups restrict RDS ingress to the ECS task security group only.

6. Secrets management:

  • API keys (Groq, OpenAI, Deepgram, ElevenLabs, Twilio) stored in AWS Secrets Manager, encrypted with KMS.
  • ECS tasks read secrets at startup as environment variables — no keys in code or Docker images.

4 AWS Infrastructure & DevOps

16 Why ECS Fargate instead of AWS Lambda for a voice IVR application?Foundational ▼

ECS Fargate wins for voice workloads because of WebSockets and statefulness:

Why ECS:

  • No cold start: Lambda cold starts (1-5s) are unacceptable for voice. ECS tasks are always warm — the WebSocket connection is established instantly.
  • WebSocket support: Twilio Media Streams require a persistent WebSocket connection for the entire call duration (minutes). Lambda has a 15-minute max timeout and doesn't natively support WebSocket servers.
  • Stateful sessions: Each ECS task maintains persistent connections to PostgreSQL, Redis, Deepgram, and ElevenLabs. Lambda would need to re-establish these connections per invocation.
  • Container flexibility: We run 2 containers per task (main app + mock API). Lambda doesn't support sidecar containers.

Why Fargate (not EC2-backed ECS):

  • No server management — AWS handles patching, scaling the underlying infrastructure
  • Pay-per-task (no idle EC2 instances during off-hours)
  • Simpler auto-scaling (no cluster capacity providers needed)

Tradeoff: Always-on cost — minimum 1 task running even with zero calls (dev: ~$15/month for 512 CPU / 1024 MB). Lambda would be $0 with no calls. But the first call on Lambda would take 5+ seconds to respond, which is a dead conversation.

17 Describe the auto-scaling strategy. Why three scaling policies instead of one?Intermediate ▼

Three independent scaling policies on the ECS service:

  1. CPU utilization (target: 60%): Catches compute-bound spikes (LLM response processing, audio transcoding). Scale-out cooldown: 60s, scale-in: 120s.
  2. Memory utilization (target: 70%): Catches memory-bound growth (conversation state accumulation, WebSocket buffers, Redis connection pools). Same cooldowns.
  3. ALB request count per target (target: 10 requests/task): This is the most important for voice — each concurrent call is a persistent WebSocket connection. 10 concurrent calls per task is the practical limit before latency degrades.

Why three? Voice workloads have different bottleneck profiles:

  • During low-traffic hours: 1 task handles all calls (CPU-bound scaling is irrelevant)
  • During traffic spikes: ALB request count triggers first (10 new calls = new task), even if CPU/memory are fine
  • During long calls with heavy API usage: Memory can spike without CPU being high (holding many conversation states in memory)

Asymmetric cooldowns: Scale-out is fast (60s) because we want to respond quickly to traffic. Scale-in is slow (120s) because we don't want to kill a task that's handling an active call — a 2-minute cooldown ensures calls finish naturally.

Capacity: Dev: 1-2 tasks. Prod: 3-5 tasks (handles ~30-50 concurrent calls).

18 Why did you add CloudFront in front of the ALB? What problem did it solve?Intermediate ▼

Problem: Browser microphone access requires HTTPS.

The system includes a web-based softphone (Twilio Client SDK in the browser) for testing and agent use. Modern browsers block getUserMedia() (microphone access) on non-HTTPS origins. The ALB was HTTP-only (no SSL certificate configured).

Solution: CloudFront as an HTTPS termination layer.

  • CloudFront provides a https://*.cloudfront.net URL with AWS-managed TLS certificate (free).
  • CloudFront → ALB communication is HTTP (internal, VPC). This is acceptable because the ALB is not publicly exposed for direct HTTP access.
  • The Twilio TwiML app webhook is pointed to the CloudFront HTTPS URL, so the softphone gets HTTPS and microphone access works.

Why not ALB HTTPS directly?

  • ALB HTTPS requires an ACM certificate, which requires a custom domain. For a dev environment, *.cloudfront.net is faster to set up and costs nothing extra.
  • CloudFront also adds edge caching (useful for static dashboard assets) and DDoS protection (AWS Shield Standard).

Fallback: For local development, Chrome's --unsafely-treat-insecure-origin-as-secure flag bypasses the HTTPS requirement.

19 How is Terraform state managed? What safeguards prevent state corruption or concurrent modifications?Intermediate ▼

Remote state backend:

  • S3 bucket: ivr-terraform-state-{account_id} with versioning enabled (can roll back to previous state).
  • State key: ivr/terraform.tfstate
  • Encryption: S3 server-side encryption (SSE-S3) at rest.

State locking:

  • DynamoDB table: ivr-terraform-locks
  • When terraform apply starts, it acquires a lock in DynamoDB. If another apply is running (e.g., GitHub Actions and a developer simultaneously), the second one fails with a lock error instead of corrupting state.
  • Lock is released on completion (or can be force-unlocked in emergencies).

Pipeline safeguards:

  • GitHub Actions infra.yml is manual-trigger only (no auto-apply on push).
  • Three operations: plan (read-only), apply (creates/updates), destroy (teardown).
  • Environment selection: dev or prod — separate variable files, same state backend (different workspace or key prefix in production).

ECR exception: The ECR repository is managed outside Terraform to prevent image loss on terraform destroy. Pre-pushed images (latest, mock-api) persist across infrastructure cycles.

20 Walk me through the CI/CD pipeline. How does a code change go from PR to production?Intermediate ▼

Three GitHub Actions workflows:

1. CI (ci.yml) — triggered on push/PR to master:

Stage 1: Unit tests (no API keys)
  → pytest tests/test_utils.py (PII validators, name extraction, IDK detection)

Stage 2: Eval tests (needs Groq key)
  → eval_slots.py (PII extraction accuracy — dates, phones)
  → eval_intents.py (intent classification accuracy vs. labeled dataset)

Stage 3: E2E Twilio tests (master only, all secrets)
  → eval_e2e_twilio.py (full call via Twilio sandbox)

2. Deploy (deploy.yml) — triggered on push to master or manual:

Build:
  → Docker build → push to ECR (tags: sha-{commit}, latest)

Deploy Dev:
  → aws ecs update-service --force-new-deployment
  → Wait for service stable (health check: GET /health → 200)
  → Run E2E test against deployed dev environment

Deploy Prod:
  → Manual approval gate (GitHub environment protection rule)
  → Same ECS update + health check + E2E validation

3. Infrastructure (infra.yml) — manual trigger only:

Inputs: action (plan/apply/destroy), environment (dev/prod)
  → terraform init → terraform {action}
  → Outputs: ALB URL, CloudFront URL, RDS endpoint

Key design decisions:

  • No auto-deploy to prod — manual gate prevents accidental production changes
  • E2E tests run against deployed dev (not just in CI) — catches infrastructure issues
  • Infrastructure changes are never auto-applied — always manual trigger with explicit environment selection

5 Integration & Resilience

21 Describe the Twilio Media Stream architecture. How does audio flow from the caller's phone to your LangGraph nodes and back?Foundational ▼

End-to-end audio flow:

Caller's phone
  ↓ PSTN / SIP
Twilio (voice gateway)
  ↓ TwiML: <Connect><Stream url="wss://our-alb/stream"/>
  ↓ WebSocket (mulaw 8kHz audio packets, 20ms chunks)
ALB → ECS Task (FastAPI WebSocket endpoint: /stream)
  ↓ Forward raw audio bytes
Deepgram STT (streaming WebSocket)
  ↓ Partial + final transcriptions (JSON events)
LangGraph (router → service node)
  ↓ tts_text response
ElevenLabs TTS (streaming WebSocket)
  ↓ mulaw 8kHz audio chunks
  ↓ Back through same WebSocket to Twilio
Twilio → Caller's phone

Key implementation details:

  • Bidirectional WebSocket: The same WebSocket connection carries audio in both directions (Twilio → us for STT, us → Twilio for TTS).
  • Twilio message types: connected (stream started), media (audio chunk), stop (call ended). We send media messages back with synthesized audio.
  • Concurrent processing: STT, LLM, and TTS run as async Python coroutines. While the caller is still speaking (STT streaming), we can pre-warm connections for the response path.
  • Call control: For actions like <Dial> (transfer) or <Hangup>, we return TwiML responses to a separate REST endpoint. Twilio executes these and optionally keeps the media stream alive.
22 How are backend API integrations structured? What's the pattern for party search, holding inquiry, and payment APIs?Intermediate ▼

Centralized in /core/tools/ — each API has an async wrapper function:

core/tools/
  ├── party_search.py      # POST /party/search (phone/policy lookup)
  ├── holding_inquiry.py   # POST /holding/inquiry, /payment/history, /loan/inquiry
  ├── payment_api.py       # POST /payment/card, /payment/ach
  └── auth_token.py        # POST /auth/token (JWT acquisition)

Common pattern across all API wrappers:

  1. Async (aiohttp): All calls are non-blocking. Multiple API calls can run concurrently (e.g., policy lookup + payment history in parallel).
  2. Timeout: 10-15s per call. Voice calls can't wait longer.
  3. Structured response: Every wrapper returns { success: bool, data/error: ... }. Service nodes check success and escalate to agent on failure.
  4. Structured logging: Every call logs api_name, status_code, latency_ms, and error (first 100 chars, PII-redacted).
  5. Bearer token auth: Holding inquiry and payment APIs require Authorization: Bearer {access_token} (acquired during auth via auth_token.py).

Resilience: If the party search API is down during auth, the system doesn't block — it advances to the next collection step (manual policy entry). If a holding inquiry fails, the service node responds with "I'm having trouble accessing that right now. Let me transfer you to an agent."

23 How would the IVR integrate with an existing Avaya PBX? Describe the SIP trunk architecture and the handoff flow.Advanced ▼

Integration via Twilio Elastic SIP Trunking:

Caller → Avaya PBX → IVR Menu ("Press 3 for AI assistant")
  → SIP INVITE (with UUI headers) → Twilio SIP Trunk
  → Twilio → ALB/CloudFront → ECS (our LangGraph IVR)

Escalation (reverse):
  AI IVR → Twilio <Dial> SIP URI → Avaya PBX queue
  → Agent answers → CRM screen pop (session ID → conversation summary)

UUI (User-to-User Information) headers:

  • Avaya passes context in SIP INVITE: ANI (caller phone), account number, auth status, queue origin.
  • If UUI indicates the caller already authenticated in Avaya IVR, our system can skip re-authentication (authenticated=true from start).
  • ANI is checked first against party records — if we find a match, we skip the phone collection step entirely.

Escalation back to Avaya:

  • Transfer via SIP URI with session ID in UUI headers.
  • Agent CRM pulls conversation summary from our API (Redis + PostgreSQL) using the session ID.
  • "Warm transfer" — agent sees everything the AI discussed before picking up.

High availability: Dual SIP trunks (primary + backup). If ALB health check fails, Avaya routes to the traditional IVR as fallback — callers never hit a dead end.

24 How does the system handle partial failures? What if Deepgram goes down mid-call, or the payment API times out?Advanced ▼

Every component has a degradation path — the system never drops a call silently:

Component FailureDegradation Strategy
Deepgram STT downSwitch to OpenAI Realtime (if configured) or Twilio's built-in <Gather> STT as last resort
Groq LLM 503/429Retry 2x with exponential backoff → fall back to Bedrock → keyword matching → escalate
ElevenLabs TTS downSwitch to OpenAI TTS (tts-1, voice: nova)
Party Search API timeoutSkip ANI lookup, ask caller to provide phone/policy manually
Payment API timeout"I'm having trouble processing that right now. Let me connect you with an agent."
PostgreSQL downFall back to in-memory checkpointer (no persistence, but call continues)
Redis downSession state managed in-process only (no cross-task sharing)

Design principle: The caller should always hear a response — even if it's "I'm having trouble, let me transfer you." Silent failures (dead air) are the worst outcome in voice.

25 What are the distinct roles of PostgreSQL and Redis in this architecture? Why both?Foundational ▼

PostgreSQL (durable, relational):

  • LangGraph checkpoints: Full conversation state snapshots after every node execution. Enables session recovery on crash and historical replay.
  • Conversation store: Call history, transcripts, and metadata for the dashboard and analytics.
  • pgvector embeddings: RAG (Retrieval-Augmented Generation) support for FAQ node — insurance policy documents are embedded and queried for relevant answers.
  • Durability: Data survives ECS task restarts, deployments, and even infrastructure teardown (RDS snapshots).

Redis (fast, ephemeral):

  • Session state: Active call state with 30-minute TTL. Abandoned calls auto-expire.
  • Conversation buffering: Intermediate turn data (partial transcriptions, pending responses) that don't need persistence.
  • Cross-task sharing: If a call is handed between ECS tasks (auto-scaling), Redis provides the shared session layer.
  • Speed: Sub-millisecond reads — no point hitting PostgreSQL for ephemeral session data.

Why both? PostgreSQL for data that matters after the call (analytics, audit, recovery). Redis for data that matters during the call (session state, buffering). Using PostgreSQL for everything would add 5-10ms per session read; using Redis for everything would risk data loss on node failure.

Environment isolation: Separate databases in PostgreSQL (ivr_dev, ivr_prod), separate Redis DB slots (0=dev, 1=prod).

28 If this system needed to serve 10x the current call volume across multiple insurance brands, what architectural changes would you make?Advanced ▼

Scaling from single-brand dev to multi-tenant production:

1. Multi-tenancy:

  • Tenant-aware state: Add tenant_id to CNOState. Route to tenant-specific system prompts, API endpoints, and phone numbers.
  • Per-tenant system prompts: Insurance brand voice, compliance rules, and product catalog differ per tenant.
  • Database isolation: Schema-per-tenant in PostgreSQL (or separate databases for strict isolation).

2. Compute scaling:

  • Increase ECS max tasks: 5 → 50+ (or move to EKS for finer-grained pod scaling).
  • Horizontal scaling of WebSocket handlers with sticky sessions (ALB target group stickiness by call_sid).
  • Consider AWS App Runner or Kubernetes with KEDA for event-driven scaling.

3. LLM tier:

  • Move from single Groq account to provisioned throughput (dedicated capacity).
  • Add a model routing layer: simple intents → smaller model, complex responses → larger model.
  • Cache common responses (FAQ, greeting) to skip LLM entirely.

4. Data tier:

  • PostgreSQL → Aurora Serverless v2 (auto-scales storage and compute).
  • Redis → ElastiCache Global Datastore (cross-region replication for DR).
  • Add read replicas for analytics queries (don't query the primary during peak hours).

5. Observability:

  • Move from CloudWatch to a dedicated observability stack (Datadog, Grafana Cloud) for cross-service correlation.
  • Distributed tracing (OpenTelemetry) across Twilio → ECS → LLM → APIs.
29 What are the top 3 architectural tradeoffs you made, and what would you do differently with hindsight?Advanced ▼

Tradeoff 1: Groq (fast, less reliable) vs. OpenAI/Claude (slower, more reliable)

  • Decision: Groq for sub-200ms inference, critical for voice.
  • Cost: Groq has occasional 503s and rate limits. Required building retry + fallback logic.
  • Hindsight: Would add an automatic circuit breaker (not just retry) that switches provider after N consecutive failures in a time window. Currently the failover is manual (env var change).

Tradeoff 2: Flat graph topology (all nodes → END) vs. cyclic graph

  • Decision: No loops in the graph. Multi-turn is achieved via checkpointing + re-entry at START.
  • Cost: Every turn re-runs the router, even during auth where the next node is obvious. Adds ~150ms per turn unnecessarily.
  • Hindsight: Would add a "fast path" that bypasses the router when active_flow is set and the caller is mid-auth. The router already does this check, but it still invokes the LLM before deciding. Could be pure logic.

Tradeoff 3: Auth as guard pattern vs. dedicated auth node

  • Decision: Auth guard inside service nodes preserves intent.
  • Cost: Complex control flow — auth state machine lives across multiple files (auth_guard.py, nodes/auth.py, router redirect logic). Harder for new developers to trace.
  • Hindsight: The pattern works well, but would add a state machine diagram to the docs and explicit auth state transition tests. The complexity is justified by the UX benefit (callers don't re-state intent after auth).
30 Walk me through an entire call flow: a caller dials in, asks about their policy, authenticates, gets their policy status, then makes a payment. Trace every component involved.Advanced ▼

Complete end-to-end trace:

Phase 1: Call Setup

  1. Caller dials +19087425347 → Twilio receives the call.
  2. Twilio sends POST to /twilio/voice → TwiML response: <Connect><Stream url="wss://cloudfront-url/stream?token=WS_AUTH_TOKEN"/>
  3. WebSocket established. Twilio sends connected event with call_sid and stream_sid.
  4. ECS task opens persistent connections to Deepgram STT and ElevenLabs TTS.
  5. LangGraph initializes CNOState with call_sid, loads checkpoint (empty for new call).
  6. Greeting plays: "Thank you for calling US Insurance Company. How can I help you today?"

Phase 2: Intent Classification

  1. Caller says: "I'd like to check my policy status."
  2. Twilio sends mulaw audio packets → Deepgram STT → transcript: "I'd like to check my policy status"
  3. LangGraph: START → router. Router LLM (Groq, ~150ms): classifies as "policy_info".
  4. Conditional edge dispatches to policy_node.

Phase 3: Authentication (multi-turn)

  1. policy_node calls ensure_authenticated(state, "policy"). Auth guard sees authenticated=false.
  2. Auth step: "collecting_phone". Response: "I'd be happy to help. For security, could you please provide your phone number?"
  3. active_flow="policy" set. State checkpointed to PostgreSQL.
  4. Caller says: "555-123-4567" → Deepgram transcribes → Router sees active_flow="policy", redirects back to policy_node without LLM call.
  5. Auth guard: party_search(phone="5551234567") → API returns party record. candidate_party stored.
  6. Auth step: "verifying_dob". Response: "Thank you. And what is your date of birth?"
  7. Caller says: "January 15th, 1965" → normalize_dob() → "1965-01-15" → matches candidate_party.DOB.
  8. authenticated=true. Auth step: "collecting_caller_name". "May I ask your name please?"
  9. Caller says: "John Smith" → fuzzy match against Personas → caller_persona="insured".
  10. auth_token.py: POST /auth/token → access_token acquired.

Phase 4: Policy Inquiry

  1. ensure_authenticated() returns (True, state). Policy node proceeds.
  2. holding_inquiry(policy_number, access_token) → API returns policy details.
  3. Service LLM (Groq, ~300ms): Generates natural response from API data.
  4. Response: "Your policy XYZ1234567 is active. Your premium is $125 per month, paid through October 2026. Your coverage amount is $250,000."
  5. ElevenLabs streams TTS audio → Twilio → Caller hears the response.

Phase 5: Payment (context switch)

  1. Caller says: "I'd like to make a payment."
  2. Router LLM classifies: "payment". Context switch allowed (policy flow was complete, no "locked" or "escalate_only" blocking).
  3. payment_node: Already authenticated (reuses customer and access_token from state). No re-auth needed.
  4. Payment flow begins: amount confirmation → OTP node → DTMF card collection (locked mode) → payment JWT → POST /payment/card → confirmation number.
  5. Response: "Your payment of $125 has been processed. Your confirmation number is PAY-789456. Is there anything else I can help with?"
  6. Caller: "No, that's all. Thank you." → Router: "goodbye" → Goodbye node → "Thank you for calling. Have a great day!" → <Hangup>.

Components touched: Twilio (voice gateway), CloudFront (HTTPS), ALB (routing), ECS Fargate (compute), Deepgram (STT), Groq (LLM x2), ElevenLabs (TTS), Party Search API, Auth Token API, Holding Inquiry API, Payment API, PostgreSQL (checkpoints x12+), Redis (session state).
