05 — Authentication

Authentication Flow Detail

5-page state machine with webhook fulfillment at each validation step. IDK skip logic and multi-policy resolution built in.

1

Collect Phone Number

Entry fulfillment: "May I have the phone number associated with your account?"

@sys.phone-number (required parameter)
POST /webhook/party-search
→ Match found: go to Collect DOB → Not found: go to Confirm Phone → "I don't know": go to Collect Policy → 2x no-input: Escalate
2

Collect Policy Number

Fallback when phone not found or caller says "I don't know".

@policy-number or @last4-policy
POST /webhook/party-search
→ Match: go to Collect DOB → Multi-policy: go to Policy Selection page → No match: Escalate
3

Collect Date of Birth

Verification against party record. Supports IDK skip to name fallback.

@sys.date
POST /webhook/validate-dob
→ DOB match: go to Collect Caller Name → No match: go to Collect Full Name → "I don't know": go to Collect Full Name
4

Collect Caller Name

Post-auth persona identification. "Who am I speaking with today?"

@sys.person
POST /webhook/match-persona
→ payor / insured / owner: Auth Complete → "other": Escalate to agent
✓

Auth Complete

Session parameters populated. Flow returns to the calling service flow. Access token acquired.

auth_status = "complete" caller_persona access_token finalized_party

07 — Telephony

Telephony Integration Options

Three paths to connect PSTN callers to your Dialogflow CX agent, from simplest to most customizable.

Option A

DFCX Phone Gateway — Simplest
PSTN → Google Phone Gateway → DFCX
No Twilio needed. Google-managed number.
  • Zero telephony code
  • Built-in STT/TTS
  • Quick setup (minutes)
  • Limited audio control
  • No barge-in tuning
  • No recording access

Option B

Twilio + CCAI Connector — Balanced
PSTN → Twilio → <Connect> → DFCX
Twilio CCAI integration via VirtualAgent verb.
  • Keep existing Twilio number
  • Recording + analytics
  • DTMF passthrough
  • Barge-in support
  • Twilio + GCP costs

Option C

Custom Media Streams — Full Control
Twilio WS → Middleware → DFCX Streaming API
Custom WebSocket bridge like current twilio_stream.py
  • Maximum audio control
  • Custom VAD/barge-in
  • Mix STT providers
  • Most code to maintain
  • Higher latency risk
Option B — Twilio TwiMLXML
<Response>
  <Connect>
    <VirtualAgent
      connectorName="dialogflow-cx"
      projectId="your-gcp-project"
      agentId="your-dfcx-agent-id"
      languageCode="en-US" />
  </Connect>
</Response>

09 — Migration Plan

Implementation Roadmap

8-phase migration plan across 8 weeks. Authentication and webhook deployment run in parallel.

Phase 1 GCP Project Setup & DFCX Agent

Week 1 ▾
  • Create GCP project, enable Dialogflow CX API, Cloud Run API, Cloud SQL API
  • Create DFCX agent in us-central1 with en-US language
  • Configure speech settings: telephony model, barge-in, DTMF, endpointing
  • Create all 15 intents with 10-20 training phrases each
  • Create custom entities: @policy-number, @last4-policy
  • Set up Default Start Flow with greeting page and intent routes
  • Configure IAM: service accounts for Cloud Run → DFCX, Secret Manager access
  • Set up Secret Manager with CNO API credentials, Twilio keys
Effort:3-4 days
Dependencies:GCP billing account
Deliverable:Working DFCX agent with intents

Phase 2 Build Authentication Flow

Week 2-3 ▾
  • Create Authentication Flow with 5 pages (Phone, Policy, DOB, Name, Complete)
  • Configure page-level parameters with required entity types
  • Set up no-match and no-input event handlers (replaces slot retry counters)
  • Add IDK intent handling on each page → skip to next step
  • Wire webhook fulfillments: party-search, validate-dob, match-persona
  • Implement Route Group "Require Authentication" with condition check
  • Apply Route Group to all 8 restricted service flows
  • Add multi-policy selection page (if party search returns multiple policies)
  • Implement persona gate: "other" persona → escalation
  • End-to-end testing: phone auth, policy auth, DOB skip, name fallback
Effort:8-10 days
Dependencies:Phase 1 + webhook service
Deliverable:Complete auth flow with all paths
Risk:Most complex phase

Phase 3 Deploy Webhook Service (Cloud Run)

Week 2-3 (parallel) ▾
  • Create FastAPI/Flask webhook service with DFCX request/response format
  • Port party_search.py, auth_token.py to webhook endpoints
  • Port holding_inquiry.py, payment_api.py to webhook endpoints
  • Add validate-dob and match-persona endpoints
  • Set up Cloud SQL (PostgreSQL) + pgvector extension
  • Set up Memorystore (Redis) for caching
  • Create Dockerfile and deploy to Cloud Run
  • Configure Cloud Run → Cloud SQL private connection
  • Set up CI/CD pipeline (Cloud Build) for auto-deploy on push
  • Load test webhook endpoints (target: <200ms p95 latency)
Effort:6-8 days
Dependencies:Phase 1 (GCP project)
Deliverable:Deployed Cloud Run service

Phase 4 Build Service Flows

Week 3-5 ▾
  • Policy Info Flow: single page, webhook to /policy-inquiry, LLM response
  • Payment Flow: webhook + GROUP G4 verbatim payment disclosure
  • OTP Payment Flow: DTMF collection pages (card_number, expiry, cvv, amount), PCI compliance, ACH auth script page
  • Loan Flow: webhook to /loan-inquiry
  • Beneficiary Flow: webhook + GROUP G2 relationship restriction verbatim
  • Contact Change Flow: multi-page (ask what, collect address/phone, confirm, submit)
  • Document Flow: enforce GROUP G3 mail/fax only delivery policy
  • Privacy Flow: GLBA disclosure page + GROUP F5 opt-out script verbatim
  • FAQ Flow: wire to Vertex AI Search or /webhook/faq
  • Escalation Flow: single page, trigger Twilio transfer
  • Goodbye Flow: single page, hang up
  • Context switch config: locked (OTP), escalate_only (services), open (FAQ)
Effort:10-12 days
Dependencies:Phase 2 + 3
Deliverable:All 13 flows operational

Phase 5 Connect Twilio via CCAI

Week 5 ▾
  • Set up CCAI integration in GCP (Dialogflow CX → Twilio connector)
  • Create Twilio Studio Flow or TwiML app with <Connect><VirtualAgent>
  • Configure Twilio phone number to point to new CCAI endpoint
  • Test inbound calls end-to-end: greeting → auth → service → hangup
  • Configure DTMF passthrough for OTP payment collection
  • Set up call recording via Twilio (mirrors current recording-status webhook)
  • Test barge-in behavior and tune speech settings
Effort:3-4 days
Dependencies:Phase 4 (all flows built)
Deliverable:Working phone number

Phase 6 Migrate RAG to Vertex AI Search

Week 5-6 ▾
  • Create Vertex AI Search data store with FAQ documents
  • Ingest existing knowledge base (from pgvector) into Vertex Search
  • Connect DFCX FAQ flow to Vertex AI Search data store
  • Configure Generative AI features for grounded FAQ responses
  • Test FAQ coverage: compare Vertex AI answers vs current pgvector RAG
  • Fallback: keep /webhook/faq as backup if Vertex coverage is insufficient
Effort:4-5 days
Dependencies:Phase 4 (FAQ flow)
Deliverable:Grounded FAQ responses

Phase 7 Testing & Compliance Validation

Week 6-7 ▾
  • PCI compliance: verify DTMF-only card collection, no TTS/STT of card numbers
  • GLBA compliance: verify verbatim GROUP F5 privacy script delivery
  • Regulated content: verify GROUP G2, G3, G4 verbatim messages unchanged
  • Auth edge cases: IDK at every step, max retries, multi-policy, "other" persona
  • Context switch: verify locked OTP (no intent routes), escalate-only suppression
  • Stress test: 50 concurrent calls via Twilio load testing
  • Latency benchmark: target <2s end-to-end response time
  • Regression test all 12 intent paths with 5 test scripts each
  • UAT with Colonial Penn stakeholders
Effort:7-8 days
Dependencies:Phase 5 + 6
Deliverable:Compliance sign-off

Phase 8 Production Cutover

Week 7-8 ▾
  • Deploy DFCX agent to production environment (create version + deploy)
  • Set up Cloud Monitoring dashboards: latency, error rate, intent match rate
  • Configure alerting: webhook failures, high no-match rate, latency spikes
  • Canary deployment: route 10% of calls to DFCX, 90% to LangGraph
  • Monitor for 48 hours, compare metrics side-by-side
  • Ramp up: 25% → 50% → 100% over 1 week
  • Decommission LangGraph infrastructure after 2-week parallel run
  • Update operator dashboard to show DFCX analytics
  • Documentation handoff and runbook creation
Effort:5-6 days
Dependencies:Phase 7 sign-off
Deliverable:Production live
10 — Trade-offs

Gains & Losses

What you gain and lose by migrating from LangGraph to Dialogflow CX.

✓ What You Gain

  • No LLM router needed — DFCX NLU handles intent classification natively
  • Built-in STT/TTS — no Deepgram/ElevenLabs dependency or cost
  • Visual flow builder — non-dev team members can modify flows
  • Built-in retry/no-input handlers — replaces manual slot retry counters
  • Native Twilio CCAI connector — simpler than custom WebSocket middleware
  • Built-in conversation analytics — intent coverage, flow metrics, session logs
  • Multi-language support — add Spanish or other languages easily
  • Versioning & environments — draft / staging / production built in
  • Managed infrastructure — no server maintenance, auto-scaling
  • Compliance audit trail — all conversations logged by default

✗ What You Lose

  • LLM flexibility — pattern-based NLU less flexible than Groq/Llama for ambiguous queries
  • RAG control — pgvector RAG is more customizable than Vertex AI Search
  • Auth elegance — state machine spread across pages vs single ensure_authenticated()
  • Vendor lock-in — fully tied to Google Cloud Platform
  • Cost at scale — $20/1000 sessions can exceed self-hosted Groq at high volume
  • Audio fine-tuning — less granular than custom WebSocket pipeline
  • Real-time API option — can't easily use OpenAI Realtime for auth mode
  • Custom barge-in — VAD-level control lost with managed telephony
